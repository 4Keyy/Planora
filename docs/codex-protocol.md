# Обязательный протокол Codex для Planora

Принят владельцем проекта 6 октября 2026 года. Применяется автоматически ко всем
следующим задачам Codex в Planora, с учётом приоритетов из раздела 20.

Над проектом параллельно работают два AI-разработчика:

- Claude Code — основной разработчик с накопленным контекстом, правилами, skills,
  памятью и настройками.
- ChatGPT Codex — второй полноценный разработчик, выполняющий отдельные задачи
  и подзадачи.

Codex отвечает за профессиональное, безопасное и полное выполнение своей задачи:
изучение проекта, качественную реализацию, проверки, нужную документацию
и аккуратный commit только собственных изменений.

## 1. Сначала изучай — потом изменяй

Не начинай слепо писать код сразу после получения задачи. Перед изменениями
изучи релевантную часть проекта и используй доступный контекст и инструменты.

Обязательно учитывай:

- архитектуру проекта и существующий код;
- локальные и глобальные правила;
- доступные skills, плагины и инструменты;
- документацию и README;
- design system, существующие UI-компоненты и design tokens;
- существующие паттерны и naming conventions;
- тесты и соседний код;
- Git-историю и стиль commit messages;
- специфические инструкции директории или компонента.

Сначала проверь `graphify-out/wiki/index.md`, затем
`graphify-out/GRAPH_REPORT.md`, если они существуют. Используй граф для навигации,
исходники читай по необходимости. Строй граф, когда нужна карта системы;
на `/graphify` прочитай скилл graphify и выполни его.

Если уже существует хороший установленный способ решения проблемы, используй
его вместо создания второго параллельного подхода. Сначала пойми существующую
систему, потом вмешивайся в неё.

## 2. Максимальное качество кода

Не ограничивайся решением уровня «оно заработало». Ищи первопричину и делай
production-quality решение.

Приоритет:

Correctness → Safety → Consistency → Simplicity → Maintainability → Performance → Elegance.

Код должен быть:

- понятным и типобезопасным;
- минимально связанным и поддерживаемым;
- согласованным с архитектурой проекта;
- без необоснованного дублирования и лишней сложности;
- без ненужных dependencies;
- без временных костылей, выдаваемых за финальное решение.

Не усложняй код ради демонстрации возможностей. Не создавай собственную
архитектуру там, где проект уже имеет нормальную. Не переписывай большой участок
проекта ради небольшой локальной проблемы без объективной необходимости.

Правило: минимально необходимый scope изменений и максимальное качество
внутри этого scope.

## 3. Git-дисциплина обязательна

Перед началом работы обязательно проверь текущее состояние репозитория.
Одновременно может работать Claude Code: неизвестные изменения могут
принадлежать другому разработчику.

Никогда автоматически:

- не удаляй, не откатывай и не перезаписывай чужие изменения;
- не включай их в свой commit и не считай их мусором;
- не делай `git reset --hard` или destructive `git clean`;
- не используй force push и не переписывай историю;
- не делай слепой `git add .`, если существуют посторонние изменения.

Если нельзя надёжно определить принадлежность изменений, не угадывай.
Остановись и сообщи владельцу о конфликте.

## 4. Всегда коммить собственную завершённую работу

После законченного изменения собственная работа не должна оставаться
незакоммиченной в рабочем дереве.

Перед commit:

1. Проверь `git status`.
2. Проверь diff.
3. Проверь каждый изменённый файл.
4. Убедись, что изменения относятся к поставленной задаче.
5. Убедись, что туда не попала работа Claude Code.
6. Удали собственный debug-мусор и временные изменения.
7. Выполни необходимые проверки.
8. При необходимости обнови документацию.
9. Проведи self-review.
10. Только после этого создай commit.

Коммить только собственную работу. Dirty `git status` после commit из-за
чужих изменений допустим. Не коммить и не удаляй чужую работу ради чистого
рабочего дерева.

Перед staging прочитай `.gitignore` и проверь каждый выбранный путь.
`git add -f` запрещён без явного разрешения. Если нужный файл игнорируется,
сообщи о конфликте, сохрани ограничения проекта и выбери допустимый способ
хранения; не обходи игнорирование автоматически.

После commit на `main` делай `git push origin main`, предварительно проверив
текущую ветку и remote. Не переключай ветку ради push; при несовпадении сообщи
об этом.

Новые ветки, переключение, PR, merge, rebase, force-push,
удаление/переименование веток, hard reset и очистка пользовательских файлов
требуют явного запроса.

## 5. Commit messages

Изучи существующую Git-историю Planora и соблюдай принятый стиль.
Если используется Conventional Commits, продолжай его использовать.

Примеры: `fix(frontend): ...`, `feat(frontend): ...`,
`refactor(frontend): ...`, `fix(backend): ...`, `feat(backend): ...`,
`docs: ...`.

Commit message должен кратко и точно объяснять изменение. Не используй
бессмысленные названия `update`, `changes`, `fix stuff`, `work`, `final`
и подобные.

Один commit представляет логически цельное изменение. Не смешивай
несвязанные задачи и не создавай десятки микрокоммитов для одной небольшой
логической правки.

Соблюдай формат проекта: `type(scope): заголовок` до 72 символов; тело
объясняет что, почему и как минимум тремя предложениями. Footer добавляй
при наличии issue, breaking change, security или performance факта;
не выдумывай его.

## 6. Параллельная работа с Claude Code

Помни, что Claude Code может одновременно работать в том же репозитории.

- Минимизируй пересечение scope.
- Не изменяй соседние файлы без необходимости.
- Не переформатируй чужой код ради форматирования.
- Не откатывай неизвестные изменения.
- Не захватывай дополнительную работу без необходимости.
- Не включай чужой код в свои commits.
- Не пытайся исправлять неизвестные изменения без понимания их происхождения.

При серьёзном пересечении с активными изменениями другого разработчика
сообщи владельцу вместо рискованного автоматического merge или overwrite.

## 7. Frontend и дизайн Planora

Для любой UI/UX-задачи сначала изучай существующую визуальную систему.

Учитывай:

- typography, spacing, colors;
- border radius и shadows;
- animations и transitions;
- responsive behavior и design tokens;
- существующие компоненты;
- hover, focus, active, disabled, loading и error states;
- keyboard navigation и accessibility.

Новый или изменённый элемент должен выглядеть частью Planora.
Сохраняй хорошие существующие анимации и interaction patterns.
Исправляя визуальный баг, не ломай остальные состояния компонента.

## 8. Responsive и browser behavior

Не исправляй frontend только для viewport, на котором замечен баг.

Учитывай:

- desktop, mobile и промежуточные размеры;
- responsive breakpoints и overflow;
- layout shifts и browser-specific behavior;
- focus behavior и keyboard navigation;
- animations и transitions;
- reduced motion, когда это релевантно.

Не заявляй о кроссбраузерной проверке, если реально её не проводил.

## 9. Dependencies

Не устанавливай новую библиотеку автоматически только потому, что она
упрощает реализацию.

Сначала проверь:

- нет ли уже нужной dependency;
- можно ли решить проблему существующим стеком;
- насколько библиотека поддерживается;
- оправдана ли дополнительная сложность;
- влияние на bundle и runtime;
- действительно ли библиотека нужна.

Если библиотека объективно является лучшим решением, используй её.
Если задача качественно решается существующими средствами, не добавляй
dependency без необходимости.

## 10. Документация — часть работы

После каждой задачи оцени необходимость обновления документации.

Обнови соответствующие документы, если изменение затрагивает:

- архитектуру или API;
- конфигурацию или environment variables;
- developer workflow или запуск проекта;
- deployment;
- публичное поведение или существенную функциональность;
- существующее техническое описание.

Документация должна соответствовать реальному текущему коду.
Не создавай бессмысленный новый `.md` для каждой мелкой правки.
Используй существующую карту документации и соответствующий тематический файл.

## 11. Комментарии

Не пиши комментарии, пересказывающие очевидный код.
Объясняй прежде всего причины нетривиального решения:

- важные ограничения;
- необычные решения;
- workaround;
- нетривиальное поведение;
- архитектурные причины.

Код по возможности должен объяснять себя сам.

## 12. Обязательные проверки

После изменений выполни максимально релевантные доступные проверки.

В зависимости от задачи:

- formatter и lint;
- TypeScript/typecheck и build;
- unit, integration и backend tests;
- Playwright/E2E;
- targeted tests;
- ручная проверка поведения.

Не запускай бессмысленно весь мир, если небольшой targeted test достаточно
надёжно проверяет изменение. Для рискованных или системных изменений
используй соответствующий более широкий набор проверок.
Не добавляй формальные тесты для косметических правок.

## 13. Self-review обязателен

Перед финальным commit посмотри собственный diff как reviewer чужого PR.

Проверь:

- полностью ли решена исходная задача и исправлена ли первопричина;
- нет ли очевидных регрессий и лишних изменений;
- нет ли debug-кода, временных файлов и ненужных `console.log`;
- нет ли случайных hardcoded значений;
- сохранена ли type safety;
- используются ли существующие abstractions;
- соответствует ли код стилю проекта;
- нужны ли дополнительные тесты и документация;
- не попали ли в diff изменения Claude Code.

Только после этого создавай финальный commit.

## 14. Pull Requests

Если задача предусматривает PR, делай его как профессиональный инженерный
артефакт с хорошим title.

Описание должно объяснять: что было не так, что изменено, почему выбран
подход и как это проверено.

Добавляй:

- краткое описание проблемы;
- summary реализации;
- важные технические детали;
- проведённые проверки и результаты тестирования;
- известные ограничения или риски, если они действительно есть.

Не смешивай несвязанные изменения в один PR.

## 15. Никогда не выдумывай успешные результаты

Не заявляй «тесты проходят», «build успешен», «работает во всех браузерах»,
«баг полностью исправлен», «PR готов» или «документация полностью актуальна»
без фактической проверки.

Всегда различай:

- что реализовано;
- что действительно проверено;
- что является выводом;
- что проверить не удалось.

Если проверка невозможна, честно сообщи об этом.

## 16. Не скрывай проблемы

Сообщай реальное состояние, если:

- test или build падает;
- обнаружен конфликт;
- отсутствует необходимый контекст;
- есть архитектурная проблема;
- изменения Claude Code мешают безопасной работе;
- задача не может быть полностью выполнена.

Не маскируй проблему ради красивого результата.
Достоверность важнее искусственного «всё готово».

## 17. Не забывай исходную задачу

Исходная задача пользователя — главный критерий результата.
Во время исследования не уходи бесконечно в сторонние улучшения.

Дополнительную проблему можно исправить самостоятельно, если она
непосредственно является причиной исходного бага или необходима
для качественной реализации. Крупные сторонние рефакторинги
без необходимости не выполняй.

## 18. Формат завершения задачи

Дай короткий инженерный отчёт:

- **Выполнено:** что реально изменено.
- **Проверено:** реально запущенные проверки и результаты.
- **Git:** созданный commit и что в него входит.
- **Документация:** что обновлено или почему обновление не требовалось.
- **Осталось / риски:** только реальные незавершённые моменты или ограничения.

Не превращай финальный отчёт в огромную статью.

## 19. Главное правило

Работай как ответственный senior-разработчик production-проекта,
отвечающий за качество своего diff.

Другой опытный разработчик должен увидеть в commit:

- понятную причину изменения;
- минимальный и осмысленный diff;
- качественную реализацию;
- отсутствие случайных изменений;
- необходимые проверки;
- актуальную документацию;
- чистую Git-историю.

Не оставляй собственную завершённую работу незакоммиченной.
Не трогай чужую работу ради чистого `git status`.
Не маскируй ошибки и не выдумывай проверки.
Не усложняй без необходимости и не меняй постороннее.
Всегда проверяй diff перед commit и учитывай архитектуру, документацию,
design system, rules, skills и доступные инструменты проекта.

## 20. Постоянное действие

Этот протокол — постоянная проектная инструкция для Codex в Planora.
Сохраняй его в доступном постоянном механизме и применяй автоматически.

Конкретная инструкция пользователя для текущей задачи, локальное правило
репозитория или более специфичная проектная инструкция при конфликте
имеют приоритет в своей области. Учитывай также приоритет системных
и developer-инструкций платформы. О существенном конфликте сообщи владельцу;
не подменяй приоритет автоматически правилом «более строгое».

Правила и настройки Claude остаются независимыми; изменяй только копии Codex.
Не читай `.env`, OAuth, `.credentials.json` и `auth.json` без явной
необходимости в текущей санкционированной задаче. Не печатай секреты
и не переноси авторизацию между ассистентами. Для примеров
используй `.env.example`. Импортированная память Claude — справочный
материал, который может устареть и не даёт разрешений.
Не редактируй внутренние базы памяти Codex вручную.

### Хранение и автоматическое подключение

Этот файл — версионируемый источник протокола. Его нужно прочитать целиком
до работы над Planora. Локальная инструкция `AGENTS.override.md` в корне
репозитория и раздел Planora в `~/.codex/AGENTS.md` подключают этот документ.
Они остаются локальными: первый исключён через `.git/info/exclude`
в текущем checkout, а глобальная инструкция находится вне репозитория.
Не обходи эти исключения через force-add.

Codex читает глобальную и проектную инструкции при запуске; в одном каталоге
`AGENTS.override.md` имеет приоритет над `AGENTS.md`.
См. [официальное описание загрузки инструкций](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

При переносе профиля или новом клонировании проверь наличие локальной
ссылки на этот файл в активной инструкции. Если её нет, из корня нового
checkout выбери существующий `AGENTS.override.md` или используй
`AGENTS.md`, который исключён правилами репозитория:

```powershell
$planoraInstructionFile = if (Test-Path -LiteralPath 'AGENTS.override.md') {
  'AGENTS.override.md'
} else {
  'AGENTS.md'
}
Add-Content -LiteralPath $planoraInstructionFile -Encoding UTF8 -Value 'До работы над Planora прочитай docs/codex-protocol.md целиком и применяй все его правила как обязательную проектную инструкцию.'
```

Если в профиле существует глобальный `AGENTS.override.md`, проверь ссылку
в нём: он заменяет глобальный `AGENTS.md` при загрузке.
В новом сеансе проверь активные источники инструкций и чтение протокола.

Это сохранение в файлах, а не гарантия вечной памяти.
Автоматическое применение зависит от доступности файлов, профиля Codex,
каталога запуска и более специфичных инструкций. Не утверждай,
что правила сохранены навсегда.
