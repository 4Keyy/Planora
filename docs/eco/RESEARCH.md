# Planora Eco — исследование предметной области

- Статус: **исследование**, не план реализации. Ни одной строки кода, ни одной оценки сроков.
- Дата: 2026-09-12
- Цель: ответить на вопрос «как построить работу с личными финансами так, чтобы это приложение хотелось открывать ради удовольствия», с точностью, достаточной для того, чтобы план реализации стал очевиден.
- Метод: разбор существующего кода Planora → разбор индустрии → разбор причин отказа → доменная модель → метрики → интерфейс → хранение → сцепки → нейминг.

**Как читать пометки достоверности.** Утверждения о чужих продуктах сопровождаются источником. Там, где цифра взята из вторичного SEO-источника сомнительного качества, стоит явная пометка `[не проверено]`. Там, где вывод мой, стоит `[вывод]`. Там, где нужна проверка руками, стоит `[требует проверки]`. Выдуманных цифр в документе нет: если числа нет, написано, что его нет.

## Блок 0 — Опора на существующее

Всё, что предложено дальше, обязано быть совместимо с тем, что уже построено. Этот блок фиксирует границы.

### 0.1 Что уже есть: сервисы и слои

Шесть доменных сервисов, каждый со своей базой: Auth, Todo, Category, Messaging, Collaboration, Realtime (`docs/architecture.md:56`). Эталон четырёхслойки — Todo: `Api` (контроллеры, `Program.cs`, gRPC-сервисы) → `Application` (CQRS-команды и запросы, валидаторы, DTO, обработчики) → `Domain` (сущности, value objects, доменные события, исключения) → `Infrastructure` (EF Core, репозитории, внешние клиенты) (`docs/architecture.md:66`). В Todo это 110 файлов `.cs`, разложенных по одной папке на фичу: `Features/Todos/Commands/CreateTodo/{Command,Handler,Validator}.cs`. Эта гранулярность — принятый стиль, и Eco обязан его повторить.

Детали эталона, на которые Eco опирается напрямую:

| Что | Где | Почему важно для Eco |
|---|---|---|
| Агрегат с приватными сеттерами и статической фабрикой `Create`, проверяющей инварианты в момент создания | `Services/TodoApi/Planora.Todo.Domain/Entities/TodoItem.cs:61`–`:88` | Транзакция Eco — агрегат с тем же контрактом: проводки мутируются только через корень |
| Оптимистичная блокировка через системную колонку PostgreSQL `xmin`, без отдельной колонки и миграции | `Services/TodoApi/Planora.Todo.Infrastructure/Persistence/TodoDbContext.cs:24`–`:32` | Бесплатная защита от конкурентной правки одной транзакции с двух устройств |
| Отдельная схема на сервис: `HasDefaultSchema("todo")` | `.../TodoDbContext.cs:19` | Eco → схема `eco` в собственной базе `planora_eco` |
| `BaseEntity`: `Guid Id`, `CreatedAt/UpdatedAt/DeletedAt`, `IsDeleted`, коллекция доменных событий | `BuildingBlocks/Planora.BuildingBlocks.Domain/BaseEntity.cs:1`–`:34` | Ключи уже `Guid` и генерируются приложением (`Guid.NewGuid()` в конструкторе, `:18`) — это открывает дорогу к клиентской генерации id и идемпотентной записи |
| Базовый `ValueObject` с `GetEqualityComponents()` | `BuildingBlocks/Planora.BuildingBlocks.Domain/ValueObject.cs:3` | `Money` — value object, а не два поля рядом |
| Outbox/Inbox, `Result`/`Error`, CQRS-абстракции, пагинация, кэш, логирование | `BuildingBlocks/Planora.BuildingBlocks.*` | Eco не пишет свою инфраструктуру ни на йоту |
| Маршрут шлюза `/todos/api/v1/{everything}` → `127.0.0.1:5100` | `Planora.ApiGateway/ocelot.json:159` | Eco = `/eco/api/v1/{everything}` → новый порт. Занято: 5030 Auth, 5032 Realtime, 5058 Messaging, 5060 Collaboration, 5100 Todo, 5281 Category |
| SLO: p95 аутентифицированного чтения ≤ 400 мс; свежесть outbox p95 ≤ 60 с | `docs/slo.md:46`, `docs/slo.md:79` | Бюджет задержки дашборда Eco задан заранее, и он не щедрый |

Интеграция между сервисами устроена жёстко: синхронно — только gRPC по контрактам из `GrpcContracts/Protos` (`docs/architecture.md:158`), асинхронно — только через транзакционный outbox с идемпотентным inbox на стороне потребителя (`docs/architecture.md:196`–`:219`). Живой UI — один SignalR-сокет, мультиплексирующий три потока, где полезная нагрузка это тонкий сигнал «id + действие», а клиент дозапрашивает данные через авторизованные эндпоинты (`docs/architecture.md:242`–`:247`). Последнее особенно важно: **для финансов это идеальная модель приватности — суммы никогда не летят через шину уведомлений.**

### 0.2 Инварианты, которые нельзя нарушать

`docs/INVARIANTS.md` — не пожелания, а закон. Прямо релевантные Eco:

| Инвариант | Что это значит для Eco |
|---|---|
| `INV-OWN-1` (`:11`) — каждый домен владеет своей базой, никто не читает чужие таблицы | Eco **не может** сделать FK на `todo.todo_items`. Ссылки — непрозрачные id плюс gRPC для отображения |
| `INV-OWN-2/3` (`:17`, `:21`) — личность и дружбы принадлежат Auth | Совместные траты идут через `IFriendshipService`/gRPC, а не через свою таблицу друзей |
| `INV-COMM-1` (`:29`) — синхронно только gRPC, HTTP между сервисами запрещён | Новый контракт `eco.proto`, если Eco понадобится кому-то синхронно |
| `INV-COMM-2` (`:33`) — `x-service-key` на каждом gRPC-вызове | Копируется из эталона |
| `INV-COMM-3` (`:37`) — события только через outbox, `IEventBus.Publish` из хендлера запрещён | Событие «транзакция записана» пишется в `eco.outbox` в той же транзакции |
| `INV-COMM-4` (`:47`) — inbox дедуплицирует по паре (id события, тип обработчика) | Обработчики Eco обязаны быть идемпотентны под реплей |
| `INV-COMM-5` (`:51`) — частичный составной индекс `ix_outbox_messages_active` обязателен | Скопировать конфигурацию, не изобретать |
| `INV-DATA-1` (`:145`) — мутации только через методы агрегата | Проводки не редактируются напрямую |
| `INV-DATA-2` (`:147`) — `SaveChangesAsync` единственный примитив коммита, мультитабличные мутации в одной транзакции | Транзакция + её проводки + outbox-строка = один коммит. Для леджера это не удобство, а корректность |
| `INV-DATA-3` (`:149`) — `AsNoTracking()` на чтениях | Все отчёты |
| `INV-DATA-4` (`:151`) — soft-delete через глобальные фильтры | Осторожно: для леджера soft-delete опасен, см. [3.5](#35-транзакции) |
| `INV-API-2` (`:175`) — новые эндпоинты предпочитают сырой DTO, четвёртую форму ответа не вводить | — |
| `INV-OBS-2` (`:183`) — чувствительное не логируется | Расширить перечень на суммы и мерчантов, см. [6.5](#65-приватность) |
| `INV-OBS-5` (`:192`) — захват текста SQL (`CaptureDbStatementText`) выключен по умолчанию | Для Eco он должен быть выключен **навсегда**: параметры запроса — это суммы |
| `INV-PERF-1` (`:241`) — интеграционные тесты ловят N+1 через `N1SentinelInterceptor` | Отчётные пути обязаны быть под `BeginScope` |
| `INV-FLOW-1/4/5` (`:250`, `:252`, `:257`) — миграции коммитятся, в прод их катит `tools/Planora.Migrator`, дрейф схемы отвергается | — |

Операционная ловушка на будущее: `docs/database.md:41` утверждает, что репозиторий намеренно игнорирует `**/Migrations/**`, при этом `INV-FLOW-1` требует коммитить миграцию вместе со схемным изменением, и фактически миграции в репозитории есть. Для Eco это значит: **при первом схемном изменении убедиться, что миграция реально попала в индекс git, а не растворилась в `.gitignore`.**

### 0.3 Визуальный язык: что уже принято

Источник истины — `frontend/src/lib/design-tokens.ts:9`–`:231`. Из него следует характер продукта, и он неожиданно удобен для денег:

- **Основной цвет — чистый чёрный** (`primary.DEFAULT: '#000000'`, `:33`), акцент — голубой `#0ea5e9` (`:49`). Продукт монохромно-нейтральный; цвет в нём редкость, а не фон. Для финансов это подарок: уже есть визуальная культура, в которой число может быть просто чёрным.
- **Серая шкала 50–900** (`:17`–`:29`) и **серая шкала графиков** `--chart-1…--chart-5` (`frontend/src/app/globals.css:136`–`:140`) — уже монохромные. Текущая система по умолчанию не раскрашивает данные, и это верная точка старта, см. [5.8](#58-цвет).
- **Радиусы** 6/10/14/16/20/24 px (`design-tokens.ts:117`–`:126`); карточки `rounded-2xl` с **прозрачным фоном** (`frontend/src/components/ui/card.tsx:11`), потому что под ними живёт декоративный WebGL-градиент ColorBends (`frontend/src/components/backgrounds/color-bends.tsx`, шейдер с `:21`).
- **Тени мягкие, многослойные** (`design-tokens.ts:133`–`:140`); фокус — кольцо, а не обводка (`:143`).
- **Кнопки**: `active:scale-[0.96]`, `hover:translate-y-[-2px]`, `focus-visible:ring-4`, высоты 36/40/48 px (`frontend/src/components/ui/button.tsx:8`–`:38`). Тактильность уже в языке.
- **Шрифт Plus Jakarta Sans** (`globals.css:117`), подключён через `@fontsource` весами 300–800 (`frontend/src/app/layout.tsx:2`–`:7`).
- **Табличные цифры уже используются**: `tabular-nums` вместе с `font-black` встречается в шапке задач и в профиле (`frontend/src/app/tasks/page.tsx:94`, `frontend/src/app/profile/page.tsx:224`). Привычка «числа выравниваются» в проекте есть.
- **Мобильные основы заложены**: снятие тап-подсветки и `touch-action: manipulation` (`globals.css:465`–`:470`), пин 16 px для полей ввода против зума iOS (`globals.css:476`–`:483`), хелперы safe-area (`:487`–`:488`), жёсткий запрет горизонтального скролла документа (`:29`–`:38`).
- **Навигация** — три вкладки: Dashboard, Tasks, Categories (`frontend/src/components/layout/navbar.tsx:22`–`:25`). Eco — четвёртая. На мобильном это «пилюля» с выдвижным меню (`navbar.tsx:438`).
- **Хаптика** есть и уже дисциплинированная: `tap: 8` мс, `success: [10, 28, 14]`, только для редких значимых действий, с уважением к `prefers-reduced-motion` (`frontend/src/lib/haptics.ts:12`–`:27`).

### 0.4 Язык движения: что уже принято

`frontend/src/lib/animations.ts` — готовый контракт, и он прямо называет автора принципов (Emil Kowalski, `:4`):

- только GPU-композитные свойства, `transform` и `opacity`; никаких `filter`/`blur`, никаких теней в `whileHover`, никакого `transition: all` (`:5`–`:9`);
- **UI-взаимодействия ≤ 300 мс, визуализация данных до 1500 мс допустима** (`:6`) — прямое разрешение на «длинную» анимацию графика;
- тайминги: `DURATION_INSTANT = 0.1` (`:27`), `FAST = 0.18` (`:30`), `UI = 0.22` (`:33`), `DELIBERATE = 0.28` (`:36`), `DATA_VIZ = 1.5` (`:39`);
- кривая по умолчанию — экспоненциальный выход `[0.16, 1, 0.3, 1]` (`:16`); пружины `SPRING_STANDARD` 400/28 (`:47`) и `SPRING_RESPONSIVE` 416/20 (`:57`);
- `prefers-reduced-motion` соблюдается дважды: глобально через `MotionConfig` и в CSS сжатием всех keyframes до 0.01 мс (`globals.css:490`–`:502`) — намеренно «почти мгновенно», а не «выключено», чтобы смена состояния оставалась читаемой. Это важная деталь философии: **движение убирают, сигнал сохраняют.**

И главное: **паттерн «числовой роллер» в проекте уже изобретён.** `StatusPill` (`frontend/src/app/tasks/page.tsx:74`–`:104`) при изменении счётчика прокручивает цифру по вертикали через `AnimatePresence mode="popLayout"` за 0.2 с — по комментарию в коде, «чтобы живые обновления читались как счётчик, а не как жёсткая подмена». Для Eco это не идея, которую надо придумать, а компонент, который надо поднять в общий слой и назвать `<Amount>`.

### 0.5 Дыры, которые Eco обнажит

Честный список того, чего в проекте **нет** и что Eco потребует как новое решение:

1. **Тёмной темы нет.** `globals.css:15`–`:25` прибивает `color-scheme: light` и белый фон, с объяснением в комментарии: контент лежит на прозрачных поверхностях поверх градиента ColorBends, спроектированного под белое, и при системной тёмной теме получалось «тёмное на тёмном». Блок `.dark` с токенами существует (`globals.css:151`), но не активирован. Тёмная тема для Eco — **новое продуктовое решение с реальной ценой**: второй набор цветов графиков, второй набор цветов шейдера, ревизия всех прозрачных поверхностей.
2. **Библиотеки графиков нет.** В `frontend/package.json:19`–`:49` нет ни recharts, ни d3, ни visx, ни chart.js. Зато есть `three` (`:45`) — WebGL уже в бандле — и `framer-motion` (`:38`). Развилка разобрана в [5.4](#54-визуализация-что-работает-и-что-врёт).
3. **Нет ни денежного типа, ни валюты, ни курса** — домен девственный.
4. **`force-dynamic` на весь App Router** (`docs/DECISIONS/0006-force-dynamic-and-csp-nonce.md`): каждая страница рендерится на запрос, чтобы CSP-нонс был per-request. Значит статического префетча не будет, TTFB платит за SSR, и весь бюджет p95 ≤ 400 мс расходуется на сервере.
5. **`<html lang="en">`** (`frontend/src/app/layout.tsx:74`) при русскоязычном продукте. Для задач это косметика; для денег нет: скринридер прочитает «12 345 ₽» английским голосом. Eco делает этот баг заметным.
6. **Табличные цифры в Plus Jakarta Sans под вопросом.** Класс `tabular-nums` в коде есть, но поддерживает ли шрифт OpenType-фичу `tnum`, по бинарнику woff2 проверить не удалось (brotli-сжатие). `[требует проверки]`; метод — отрендерить `1111` и `0000` одним весом и сравнить ширину в DevTools: если равны, фича есть. Если нет, `tabular-nums` это молчаливый no-op и все денежные колонки будут «дышать». План Б — в [5.7](#57-типографика-чисел).
7. **Версии.** Репозиторий на Next `^16.2.9` и React `^18.3.1` (`frontend/package.json:40`–`:42`), Tailwind 3.4 с директивами `@tailwind` (`globals.css:1`–`:3`). Это расходится с формулировкой «Next.js 14» в постановке; целимся в Next 16 / React 18 / Tailwind 3.

## Блок 1 — Ландшафт индустрии

Задача блока — извлечь не фичи, а **принципы**: почему продукт устроен так, и что именно в нём ломается.

### 1.1 Конвертные и zero-based

**YNAB** (You Need A Budget). Метод из четырёх правил: дай каждому рублю работу; учитывай настоящие расходы; катись с ударами (перераспределяй, а не вини себя); старь свои деньги. Цена $14.99/мес или $109/год, пробный период 34 дня ([StackSwitch](https://stackswitch.app/review/ynab), [The Penny Hoarder](https://www.thepennyhoarder.com/budgeting/ynab-review/)).

- Гениально: **программа — механизм принуждения к методу, а не инструмент учёта.** Бюджетируются только деньги, которые уже есть, а не прогноз дохода: это убивает главный самообман бюджетирования. Правило «катись с ударами» — встроенное прощение: перерасход в категории не ошибка, а повод перенести деньги из другой.
- Плохо: обрыв на входе. Обзоры сходятся, что метод «щёлкает» не сразу и первые 2–3 недели требуют усилия ([StackSwitch](https://stackswitch.app/review/ynab)). Плюс цена — один из самых дорогих продуктов категории.
- Ключевая идея: **ограничение до данных.** Сначала решение, потом учёт.
- Почему уходят: цена плюс необходимость ежедневного обслуживания. Метод работает ровно до той недели, когда пользователь его не обслужил.

**Actual Budget.** Открытый код, local-first: каждый бюджет — отдельный файл SQLite, синхронизация между устройствами на CRDT, опциональное сквозное шифрование; автор James Long ([DeepWiki](https://deepwiki.com/actualbudget/actual), [обзор](https://www.jgiesing.com/actual-budget-finally-a-budgeting-app-that-respects-your-data/)).

- Гениально: **офлайн не режим, а основа.** Владение данными подано как фича, а не как уступка.
- Плохо: требует самостоятельного хостинга сервера синхронизации; мобильный опыт вторичен к десктопу.
- Ключевая идея: **данные пользователя не должны зависеть от жизни компании.** Прямой ответ на смерть Mint.
- Почему уходят: порог развёртывания. Продукт для тех, у кого есть VPS.

**Goodbudget.** Классические конверты с ручным вводом и общими конвертами для пары.

- Гениально: ручной ввод как способ осознанности — единственный продукт, который этого не стесняется.
- Плохо: нет нормальной модели переводов и сверки; в мультивалютности беспомощен.
- Ключевая идея: **совместность как первичная функция**, а не надстройка.

### 1.2 Агрегаторы и «умные» трекеры

**Mint (мёртв).** Intuit объявил закрытие в ноябре 2023, приложение выключено 23 марта 2024, пользователей переводили в Credit Karma ([CNBC](https://www.cnbc.com/2023/11/07/budgeting-app-mint-is-shutting-down-users-are-disappointed.html), [Bloomberg](https://www.bloomberg.com/news/articles/2023-11-01/intuit-winds-down-personal-finance-app-mint-shifts-users-to-credit-karma)). При переносе сохранились подключённые счета и чистая стоимость, но **не перенеслись бюджеты, пользовательские категории, цели, напоминания о счетах и история транзакций** ([Spendify](https://spendify.money/blog/mint-shut-down-now-what/), [NerdWallet](https://www.nerdwallet.com/article/finance/mint-app-closing-what-it-means-how-to-pick-a-new-budget-service)).

- Гениально было: бесплатный автоматический учёт для десятков миллионов — Mint нормализовал саму идею PFM.
- Плохо: бизнес-модель. Бесплатно в обмен на рекламу и лиды финансовых продуктов; когда приватность стала политикой платформ, модель перестала считаться `[вывод, с опорой на объяснения в обзорах закрытия]`.
- Ключевая идея и главный урок: **если продукт бесплатный, ваши данные работают на чей-то другой P&L, и продукту конец в день, когда эта арифметика сломается.**
- Второй, недооценённый урок: **миграция — событие доверия.** Intuit потерял не пользователей, а репутацию категории: «вот в чём опасность полагаться на бесплатные сервисы» (CNBC).

**Monarch Money.** Победитель миграции: рост подписчиков примерно в 20 раз за 2024 год, в мае 2025 раунд $75 млн при оценке $850 млн ([CNBC](https://www.cnbc.com/2025/05/23/personal-finance-app-monarch-raises-75-million.html), [The Paypers](https://thepaypers.com/fintech/news/monarch-secures-usd-75-million-in-funding)).

- Гениально: **домохозяйство как первичная единица** — совместный доступ без доплаты, и платная подписка как обещание «мы не продаём ваши данные».
- Плохо: подписка ставит пол по цене и тем ограничивает рынок `[вывод]`.
- Ключевая идея: **платит пользователь — значит продукт может быть на его стороне.**

**Copilot Money.** Финалист Apple Design Awards 2024 в категории Innovation, не победитель — победил Procreate Dreams ([Apple Newsroom](https://www.apple.com/newsroom/2024/06/apple-announces-winners-of-the-2024-apple-design-awards/)). Цена $13/мес или $95/год ([Finny](https://getfinny.app/blog/copilot-money-pricing-2026)). Только экосистема Apple.

- Гениально: **красота как механизм удержания** и ежедневный ритуал «review» — разбор новых операций превращён в короткую приятную задачу с видимым концом. Автокатегоризация обучается на правках пользователя.
- Плохо: платформенная тюрьма (нет Android и веба); зависимость от американской агрегации.
- Ключевая идея: **самую нудную работу нужно не убирать, а делать приятной и конечной.** Это лучший рабочий инсайт всей категории.

**Lunch Money.** Инди-продукт одного разработчика, $10/мес, мультивалютность, API как первичная поверхность, CSV-импорт как полноправный путь ([Monavio](https://monavio.app/blog/best-copilot-money-alternatives/)).

- Гениально: **уважение к power-user.** API не приложение к продукту, а сам продукт.
- Плохо: нет инвестиций, нет планирования FI, дизайн аскетичен.
- Ключевая идея: **экспорт и API — форма доверия.**

**Empower (ранее Personal Capital).** Бесплатные дашборды чистой стоимости, монетизация через управление капиталом.

- Ключевая идея, она же предупреждение: **бизнес-модель определяет UX.** Дашборд, существующий для генерации лида, оптимизирован под «покажи, что у тебя много денег», а не под «пойми свою экономику».

**Maybe Finance.** Потрачено около $1 млн, 18 месяцев до запуска, из списка ожидания 10 000+ человек в платящих при $15/мес перешли около 50; бизнес закрыт в середине 2023, код открыт в январе 2024 под AGPLv3 ([Failory](https://newsletter.failory.com/p/3-reasons-maybe-failed), [GitHub](https://github.com/maybe-finance/maybe)).

- Три причины провала по разбору Failory: окно рынка изменилось за время разработки; ставка на сторонние интеграции (назван Plaid), которые «обещали много и не дали»; перфекционизм вместо валидации — «пытались закрыть все краевые случаи».
- Ключевая идея: **продукт, зависящий от агрегатора, наследует его ограничения**, а список ожидания не является спросом.

### 1.3 Двойная запись и «для инженеров»

**Beancount / Fava, hledger, GnuCash, Firefly III.** Двойная запись в текстовом файле; ядро — правило «сумма всех проводок транзакции равна нулю»; философия — детерминированный конвейер «файл → отчёт» ([документация Beancount](https://beancount.github.io/docs/the_double_entry_counting_method/), [BeanHub Academy](https://academy.beanhub.io/intro/beancount-and-double-entry/)). Пять типов счетов (Assets, Liabilities, Equity, Income, Expenses), и всё финансовое поведение — «переводы между ведёрками».

- Гениально: **корректность как фича, которую чувствуешь позже.** Баланс невозможно «потерять»: он выводится, а не хранится. История версионируется в git.
- Плохо: обрыв UX. Мобильного захвата нет в принципе, а именно мобильный захват — подавляющая часть реальных операций.
- Ключевая идея, которую надо украсть целиком: **инвариант «сумма = 0» как единственный источник правды о балансе.**
- Почему уходят: в эту школу не уходят — в неё не приходят. Порог входа отсекает всех, кроме инженеров и бухгалтеров.

### 1.4 Банковские суперприложения

**Monzo Trends.** Расходы по категориям и мерчантам за месяц плюс «Targets» — цель по расходам на всё или на отдельные категории, с графиком прогресса ([Monzo Help](https://monzo.com/help/monzo-perks/trends-spending-and-balance-web)).

**Revolut Analytics.** Аналитика расходов со сравнением к предыдущим периодам, срезами по категории, мерчанту, стране, валюте и карте, в столбиках/круге/линии, с прогнозом будущих расходов по текущим трендам ([Revolut](https://www.revolut.com/best-budget-planner/), [Revolut Help](https://help.revolut.com/help/accounts/budget-and-analytics/how-can-i-see-my-spending-and-income-analytics/)).

- Гениально: **нулевое трение ввода.** Банк владеет потоком транзакций, поэтому категоризация бесплатна, а история полна по определению.
- Плохо и структурно неисправимо: банк не может быть на стороне пользователя в вопросе «стоит ли это покупать». Его выручка — от оборота, кредитов и подписок. Поэтому банковская аналитика всегда описательная и никогда нормативная: она покажет, сколько ушло на доставку еды, но не скажет «это 7% твоего годового дохода, и вот чем ты за это платишь» `[вывод]`.
- Ключевая идея для нас: **с банком нельзя конкурировать по трению ввода — с ним конкурируют по смыслу.** И ещё: один банк видит только свои счета, целостной картины «вся моя экономика» у него нет по определению.

### 1.5 Европейская и постсоветская школы UX

**Toshl** — «финансовые монстры»: персонажи вместо графиков осуждения. Приём: юмор как средство снятия вины. Риск: инфантильность.

**Emma** (Великобритания, «более 3 млн пользователей» по их собственному заявлению, [emma-app.com](https://emma-app.com/)) — охота на подписки: продукт построен вокруг одного действия «найди и отмени лишнее». Ключевая идея: **одно сильное обещание вместо двадцати функций.**

**Snoop** — проактивные подсказки об экономии; куплен Vanquis Banking Group в июле 2023, веб-приложение выведено из эксплуатации в ноябре 2024 ([Wikipedia](https://en.wikipedia.org/wiki/Snoop_(company)), [Snoop](https://snoop.app/terms-privacy-noticenov24/)). Урок: агрегатор без своего банка живёт до первого поглощения.

**Дзен-мани (Zenmoney)** — российская школа: подключение к 200+ банкам России и СНГ и **чтение SMS и push-уведомлений** с автоматическим распознаванием суммы и категории ([Startpack](https://startpack.ru/application/zenmoney), [FutureBanking](https://futurebanking.ru/post/2196)).

- Ключевая идея и главное локальное знание: **без открытого банкинга поток транзакций добывается из уведомлений и выписок.** Это единственный работающий канал автоматизации в РФ.
- Оговорка `[требует проверки]`: чтение SMS на Android жёстко ограничено политиками Google Play, а на iOS невозможно в принципе. Механика Дзен-мани не переносится ни на iOS, ни в веб — то есть для Planora с её веб-фронтендом она недоступна вообще.

**CoinKeeper** — перетаскивание «монет» в категории: физическая метафора вместо формы. Гениально как игра, провально как модель: перетаскивание не выражает переводы, долги и возвраты.

**Monefy, Wallet, Money Manager** — быстрый ввод плюс круговая диаграмма. Ключевая идея: **скорость ввода бьёт функциональность** для массового пользователя. И тут же ограничение: без модели счетов и переводов такой продукт врёт в сумме уже на втором месяце.

### 1.7 Двенадцать принципов, извлечённых из ландшафта

1. Метод важнее данных: продукт должен навязывать одно полезное ограничение (YNAB), но не обрывом на входе.
2. Красота — это удержание, а не украшение (Copilot).
3. Нудную работу делают конечной и приятной, а не прячут.
4. Двойная запись обязательна внутри и запрещена наружу (Beancount + все остальные).
5. Баланс выводится, а не хранится.
6. С банками не конкурируют по трению ввода — только по смыслу.
7. Бесплатность = чужой P&L = смерть продукта по расписанию (Mint).
8. Экспорт и API — форма доверия (Lunch Money, Actual).
9. Зависимость от агрегатора наследуется как ограничение (Maybe).
10. Одно число наружу, всё остальное по клику (Whoop, Oura).
11. Прощение встроено в механику, иначе первый пропуск = уход (YNAB rule 3, Duolingo freeze).
12. Домохозяйство, а не одиночка, — естественная единица (Monarch, Goodbudget).

### 1.8 Структурное окно возможности

В России **нет работающего аналога Plaid**. Стандарты открытых API ЦБ существуют, платформа коммерческих согласий в стадии пилотирования ([ЦБ РФ](https://www.cbr.ru/fintech/api/)), но обязательность для крупнейших организаций, изначально планировавшаяся с 2026 года, перенесена на более поздний срок ([TAdviser, обзор](https://www.tadviser.ru/index.php/%D0%A1%D1%82%D0%B0%D1%82%D1%8C%D1%8F:Open_Bank_System_(%D0%9E%D1%82%D0%BA%D1%80%D1%8B%D1%82%D0%B0%D1%8F_%D0%B1%D0%B0%D0%BD%D0%BA%D0%BE%D0%B2%D1%81%D0%BA%D0%B0%D1%8F_%D0%BF%D0%BB%D0%B0%D1%82%D1%84%D0%BE%D1%80%D0%BC%D0%B0))). SMS-парсинг в вебе недоступен. Значит:

- автоматический импорт «подключил банк и забыл» **невозможен** — и это не недостаток проекта, а свойство рынка;
- **следовательно единственный путь к нулевому трению — сделать ручной ввод быстрее, чем у кого-либо в мире**, и импорт выписок — безупречным;
- и это же спасает от ошибки Maybe: у нас нет зависимости от агрегатора, потому что агрегатора нет.

Это не ограничение. Это ниша. Все западные продукты за 15 лет разучились делать ввод, потому что за них его делал Plaid. **Продукт, у которого ввод транзакции занимает 2 касания и 3 секунды, в этой категории выглядит как магия.**

## Блок 2 — Почему люди бросают финансовые приложения

Это важнейший блок. Продукт, который не решает перечисленное ниже, мёртв на третьей неделе, какой бы красивый он ни был.

### 2.0 О цифрах удержания: честное предупреждение

Публичные бенчмарки по удержанию финансовых приложений **противоречат друг другу на порядок**. Business of Apps даёт для категории Finance день-30 около 4,2%; другие сводки для fintech — 10–15% и даже 15–25%; ещё одна — D1 30% / D7 17,6% / D30 11,6% ([Business of Apps](https://www.businessofapps.com/data/finance-app-benchmarks/), [apsteq](https://apsteq.com/blog/app-retention-benchmarks/)). Различие объясняется тем, что «финансы» включают и банки (куда заходят по необходимости), и трекеры (куда заходят добровольно).

Отдельно: широко гуляющие по SEO-блогам утверждения вида «67% пробовавших бюджетное приложение назвали его бесполезным по опросу CFPB 2024», «приложения с ручным вводом теряют пользователей в 3 раза быстрее», «средний D30 у PFM равен 38%» — **проверить первоисточник не удалось, все следы ведут в блоги-агрегаторы**. Помечаю `[не проверено]` и не использую как основание.

Практический вывод: **брать эти цифры как ориентир порядка величины, а не как цель.** Единственная метрика, на которую стоит смотреть в продукте такого рода, — доля пользователей, которые на 8-й и 12-й неделе всё ещё вносят операции; AppsFlyer прямо отмечает, что для финансов D30 плохая метрика и нужны week-8/week-12 ([Business of Apps](https://www.businessofapps.com/data/finance-app-benchmarks/)).

### 2.1 Десять причин отказа и контрмеры

Для каждой причины: механизм → контрмера на уровне продукта → контрмера на уровне интерфейса → как заметить, что она сработала.

#### Причина 1. Ввод — это работа

Механизм: каждая операция требует 5–8 касаний и 15–30 секунд (открыть, «+», сумма, категория, счёт, дата, комментарий, сохранить). За день таких операций 3–10. К концу второй недели суммарная «плата» превышает субъективную пользу, и пользователь просто перестаёт.

- Продукт: целевое трение — **2 касания и ≤ 3 секунды на типовую операцию**, и **1 касание, ≤ 1 секунды на повтор недавней**. Всё, что не влезает в это окно, уходит в отложенный разбор, а не блокирует запись.
- Интерфейс: одна строка естественного ввода («кофе 350»), клавиатура открыта сразу, категория предсказывается и подтверждается тем же нажатием, что и сохранение. См. [5.3](#53-ввод-транзакции).
- Метрика: медианное время от открытия до коммита, доля операций, введённых повтором, доля дней с хотя бы одной записью на 8-й неделе.

#### Причина 2. Вина от красных цифр

Механизм: приложение — единственное место, где пользователю регулярно сообщают, что он сделал плохо. Вырабатывается павловская связка «открыл приложение → почувствовал себя виноватым», а поведение, ведущее к неприятному чувству, гасится. Приложение избегается именно потому, что оно точно работает.

- Продукт: приложение **не выдаёт оценок**. Оно сообщает факт, следствие и выбор. «Осталось 6 дней и 4 200 ₽. Твой обычный темп — 1 100 ₽/день. Хватит на 3,8 дня.» Ни одного слова «перерасход», «превышение», «должен».
- Интерфейс: **красный цвет не используется для расходов вообще** (см. [5.8](#58-цвет)); отклонение от нормы показывается контрастом и весом, а не цветом тревоги. Дефицит показывается как факт длительности, а не как алый минус.
- Метрика: доля сессий, заканчивающихся действием (а не немедленным закрытием); частота открытий после «плохого» месяца по сравнению с «хорошим».

#### Причина 3. Чужие категории

Механизм: продукт поставляется с 30–40 предустановленными категориями из другой культуры потребления. Половина остаётся пустой навсегда, половина реальных трат не попадает ни в одну. Бюджет по мёртвым категориям — бессмысленный бюджет, а бессмысленный бюджет отменяет доверие ко всей аналитике.

- Продукт: **ноль категорий по умолчанию.** Категории выводятся из первых 15–25 операций пользователя, с подсказками из MCC-кодов и мерчантов, и **называются его словами**. См. [3.6](#36-категоризация).
- Интерфейс: в момент ввода предлагается 3–4 варианта плюс «новая»; создание категории — часть ввода операции, а не отдельный экран настроек.
- Метрика: доля категорий с нулём операций за 60 дней (цель — ноль), доля операций в «Без категории».

#### Причина 4. Отчёты, которые ничего не меняют

Механизм: пользователь видит, что на еду ушло 34 000 ₽, и не знает, что с этим делать. Знание без следующего шага не превращается в поведение и потому не воспринимается как ценность.

- Продукт: **правило «и что?»** — каждый экран обязан заканчиваться либо решением, либо изменённым числом. Если экран не может ответить на «что мне теперь сделать», он не выпускается.
- Интерфейс: каждый отчёт несёт одну конкретную кнопку-следствие (отменить подписку, перенести платёж, поднять лимит конверта, отложить сумму).
- Метрика: доля просмотров отчёта, завершившихся действием.

#### Причина 5. Усталость от настройки

Механизм: индустриальный стандарт онбординга — сначала счета, потом категории, потом бюджеты, потом цели. Вся стоимость настройки взимается **до** первой пользы. Пользователь платит вперёд за ценность, которую ещё не увидел.

- Продукт: **первая польза до первой настройки.** Один вопрос («сколько сейчас на основной карте?»), три операции по памяти, и сразу производное знание, которое пользователь сам посчитать не мог. Счета, бюджеты и правила заводятся позже и по поводу.
- Интерфейс: никаких мастеров. Прогрессивное раскрытие: сущность создаётся в момент, когда она первый раз нужна.
- Метрика: время до первого «aha» (цель ≤ 90 секунд, см. [5.9](#59-пустые-состояния-первый-запуск-aha-момент)), доля дошедших от установки до третьей операции.

#### Причина 6. Разрыв между «записал» и «понял»

Механизм: запись операции и понимание её последствия разнесены во времени и в пространстве интерфейса. Запись — сегодня, отчёт — в конце месяца. Обратная связь, отложенная на 30 дней, не формирует привычку.

- Продукт: **следствие показывается в момент записи.** Не «сохранено», а «сохранено; на неделю осталось 2 300 ₽ из 6 000».
- Интерфейс: тост подтверждения содержит изменившееся число, и число анимируется от старого к новому (роллер, `tasks/page.tsx:74`). Это единственное место, где анимация числа обязательна: она физически связывает действие с последствием.
- Метрика: доля записей, после которых пользователь открывает детализацию.

#### Причина 7. Ретроспективность

Механизм: продукт рассказывает про прошлое, а деньги переживаются как будущее. Тревога звучит как «хватит ли до зарплаты», а не «сколько ушло на такси в марте».

- Продукт: **прогноз — первичный экран, история — вторичный.** Главное число — не «потрачено», а «сколько можно потратить» и «когда станет тяжело».
- Интерфейс: «Кривая правды» — остаток по ликвидным счетам в прошлом и веер прогноза в будущем с зубцами обязательных платежей (см. [5.12](#512-пять-интерфейсных-идей-которых-нет-ни-у-кого), идея 1).
- Метрика: доля сессий, где пользователь взаимодействовал с будущим (сдвинул платёж, посмотрел сценарий).

#### Причина 8. Перфекционизм и разрыв с реальностью

Механизм: пользователь пропустил неделю. Цифры в приложении больше не совпадают с картой. Восстановление требует археологии. Проще бросить, чем чинить — и это рациональный выбор, потому что приложение не предлагает дешёвого способа вернуться к правде.

- Продукт: **сверка как штатный дешёвый ритуал**, а не как аудит. Приложение обязано умещать признание «я ошибаюсь на 340 ₽» в одно нажатие и легитимный счёт «Корректировка». Разойтись с реальностью — нормально; не иметь способа сойтись обратно — смертельно.
- Интерфейс: раз в неделю один вопрос «сколько реально на карте?», одно поле, три варианта разрешения разницы: найти пропущенное из списка кандидатов, создать корректировку, оставить как есть. 20 секунд. См. [3.11](#311-сверка-с-реальностью).
- Метрика: медиана |расхождение| по счетам; доля пользователей, выполнивших сверку хотя бы раз в месяц; доля вернувшихся после пропуска ≥ 7 дней.

#### Причина 9. Одиночество

Механизм: в реальности деньги общие — у пары, у семьи, у компании друзей на поездке. Продукт, который умеет только «я», вытесняется в узкую часть жизни, а совместные траты уходят в мессенджер и в отдельный Splitwise.

- Продукт: совместные пространства поверх **существующих friendships Planora** (Auth — владелец дружб, `INV-OWN-2`). Строго opt-in, с редакцией: участник видит общую трату и не видит остальной леджер.
- Интерфейс: общий «конверт» с участниками; расчёт «кто кому сколько» одной строкой; никаких лидербордов и никакого сравнения «кто больше тратит».
- Метрика: доля пользователей хотя бы с одним общим пространством; их удержание против одиночных.

#### Причина 10. Цена и недоверие

Механизм: за приложение для денег просят денег, и это правильно (см. Mint), но пользователь не знает, что будет с его данными, если продукт умрёт. История Mint сделала это осознанным страхом.

- Продукт: **полный экспорт в человекочитаемый формат с первого дня**, включая экспорт в текстовый двойной леджер (Beancount-совместимый). Явная политика: не продаём, не показываем рекламу, удаляем по требованию.
- Интерфейс: «Скачать всё» — на видном месте в настройках, а не в глубине; рядом объяснение, что именно скачивается.
- Метрика: наличие экспорта не измеряется — измеряется отсутствие оттока по причине «а что если вы закроетесь».

### 2.2 Сводка: что из этого архитектурно обязательно

Пять требований из блока 2, которые определяют схему данных, а не только UI:

1. **Черновики/Inbox** как первоклассное состояние операции (причина 1 и 6).
2. **Счёт «Корректировка» и сверка с состояниями проводки** (причина 8).
3. **Категории без предустановок, с правилами и объяснимостью** (причина 3).
4. **Прогноз как хранимый объект (повторяющиеся операции + сценарии)**, а не как расчёт на клиенте (причина 7).
5. **Совместные пространства с редакцией видимости** (причина 9), с опорой на готовый прецедент `HiddenTodoDtoFactory` и `INV-AZ-3`.

## Блок 3 — Доменная модель финансов

### 3.1 Деньги как тип

**Почему float — катастрофа.** IEEE-754 двоичный: 0.1 не представим точно, `0.1 + 0.2 != 0.3`, ошибка накапливается при суммировании тысяч строк, а сравнение на равенство перестаёт работать. Modern Treasury формулирует это прямо: «floats не годятся для хранения центов» ([Modern Treasury](https://www.moderntreasury.com/journal/floats-dont-work-for-storing-cents)). Первое правило отрасли — «никогда не использовать типы с плавающей точкой для денег» ([cardinalby](https://cardinalby.github.io/blog/post/best-practices/storing-currency-values-data-types/)).

**Развилка с весами.** Критерии и веса: точность (×5, это деньги), безопасность на границе JSON/JavaScript (×4, фронтенд на TS), пригодность для агрегации в SQL (×3), сопротивление тихой ошибке разработчика (×3), простота работы с валютами с иным числом знаков (×2).

| Вариант | Точность (×5) | Граница JS (×4) | Агрегация в SQL (×3) | Сопротивление ошибке (×3) | Мультивалютность (×2) | Итого |
|---|---|---|---|---|---|---|
| `double` / `float8` | 0 | 1 | 4 | 0 | 2 | **20** |
| C# `decimal` + PG `numeric(19,4)` | 5 | 2 | 5 | 2 | 3 | **60** |
| **`long` минорные единицы + код валюты** | **5** | **5** | **4** | **5** | **5** | **82** |

Пояснения к оценкам:

- **Граница JS.** JSON-число в JavaScript — это `double`. `numeric` из Postgres приходит либо строкой (и тогда каждый клиент обязан помнить про парсинг, иначе получит `double` молча), либо числом с потерей. Целое в минорных единицах безопасно до 2^53 ≈ 9,007×10^15 копеек, то есть до ~90 трлн ₽ — запас несопоставимо больше любого личного бюджета.
- **Сопротивление тихой ошибке.** У `numeric(19,4)` масштаб задаётся в конфигурации колонки; одна забытая настройка в новой миграции — и колонка молча округляет до целых. Целое не имеет масштаба, ошибиться нечем.
- **Агрегация.** У целых есть теоретический риск переполнения при `SUM`, но в Postgres `sum(bigint)` возвращает `numeric`, так что риска нет.
- **Мультивалютность.** ISO 4217 задаёт экспоненту: 0 знаков у JPY и KRW, 3 знака у BHD, IQD, JOD, KWD, LYD, OMR, TND, 2 знака у остального ([Datatrans](https://docs.datatrans.ch/docs/currency-codes), [ISO 4217](https://en.wikipedia.org/wiki/ISO_4217)). Хранение в минорных единицах вынуждает держать экспоненту в таблице валют с первого дня — то есть делает правильно; `decimal(19,4)` позволяет отложить вопрос до первого пользователя с иеной.

**Рекомендация.**

- Хранить `amount_minor bigint` + `currency char(3)`; экспонента берётся из справочника валют, а не из константы `100`.
- В домене — value object `Money(long AmountMinor, Currency Currency)` на базе существующего `ValueObject` (`BuildingBlocks/Planora.BuildingBlocks.Domain/ValueObject.cs:3`). Арифметика только внутри него; операции с разными валютами без явного курса — исключение, а не молчаливое приведение.
- Промежуточные вычисления (курс, проценты, деление на доли) — в `decimal` с рабочим масштабом 6 знаков, **округление ровно один раз**, в момент, когда получается хранимая сумма.
- **Округление — параметр, а не умолчание.** Для пользовательских производных величин — half-away-from-zero (соответствует школьной и бухгалтерской привычке в РФ). Для разбиения суммы на части — **метод наибольших остатков**, чтобы части складывались точно в целое: 1000 ₽ на трёх = 333,34 + 333,33 + 333,33, а не три раза 333,33 с потерянной копейкой.
- **В агрегатах не округлять вообще**: суммировать целые, округлять только при выводе.

**Отвергнуто:** `decimal`/`numeric` как основной тип. Причина отказа — граница с TypeScript и цена тихой ошибки масштаба. Оговорка: выбор легитимный, множество реальных леджеров так и сделано, и если бы фронтенд был на .NET, я бы выбрал его. Решающий вес здесь — JS.

**Отвергнуто:** хранить сумму строкой. Причина — невозможно агрегировать в SQL без приведения, а приведение возвращает нас к вопросу типа.

### 3.2 Мультивалютность

Три правила, из которых следует всё остальное.

**Правило 1. Курс хранится на операции, а не берётся «сегодняшний».** Каждая проводка несёт (а) сумму в валюте счёта, (б) сумму в базовой валюте пользователя, (в) применённый курс, (г) источник и дату курса. Пункт (б) — **осознанная денормализация**: это замороженное значение, а не вычисляемое.

**Почему отчёты не должны меняться задним числом.** Если базовая сумма считается «на лету по текущему курсу», то февраль прошлого года меняется каждый день. Пользователь открывает тот же отчёт второй раз, видит другие числа, и доверие исчезает мгновенно и навсегда. Это самая дорогая ошибка в мультивалютности, и она необратима: пересчитать назад можно, но вернуть доверие нельзя.

**Правило 2. Потоки фиксируются, запасы переоцениваются.** Различие, которое почти никто не проговаривает:

| Сущность | Что делаем | Почему |
|---|---|---|
| **Поток** (доход, расход, перевод) | Курс на дату операции, заморожен навсегда | «В марте я потратил 200 € и это стоило мне 19 400 ₽» — исторический факт |
| **Запас** (остаток на валютном счёте, актив) | Переоценка по курсу на дату «как есть» | «Сейчас на моём счёте 200 €, и это 21 100 ₽» — текущий факт |

Из разницы между двумя рождается **нереализованная курсовая разница**, и её надо показывать отдельной явной строкой, а не растворять в «прочем». Иначе чистая стоимость меняется без причины, и пользователь не понимает, разбогател он или подорожал евро. См. [4.1](#41-чистая-стоимость-и-её-разложение).

**Правило 3. Курс — это данные, а не вызов API в момент чтения.** Таблица `fx_rates(base, quote, as_of_date, rate numeric(20,10), source)` с суточной гранулярностью. Первичный источник для RUB — ЦБ РФ (официальные курсы, публикуются по рабочим днями), резервный — внешний провайдер. **Никогда не интерполировать молча**: за выходные и праздники переносится последний известный курс с явным флагом `carried_forward`, чтобы это было видно в отладке и в экспорте.

**Отвергнуто:** одновалютный MVP с колонкой `currency` и без таблицы курсов. Причина отказа — курсы нельзя добыть задним числом для операций, которые уже произошли; отсутствие исторических курсов делает ретроспективный переход в мультивалютность физически невозможным. Плюс мультивалютность возникает на первой неделе сама: подписка в долларах, поездка, покупка на зарубежном сайте.

**Отвергнуто:** пересчёт всего в базовую валюту при записи, без хранения оригинальной суммы. Причина — пользователь помнит «200 евро», а не «19 400 рублей»; потеря оригинала делает сверку с выпиской невозможной.

### 3.3 Двойная запись против плоского списка

**Что именно ломается без двойной записи.** Это не вопрос вкуса, это список поломок:

| Операция | Плоский список с типом (`expense`/`income`/`transfer`) | Двойная запись |
|---|---|---|
| Перевод с карты на вклад | Двойной счёт: либо попадёт в расходы и доходы одновременно (раздувая оба), либо требует особого типа и исключения в каждом отчётном запросе | Естественно: две проводки, сумма 0, ни в расходах, ни в доходах |
| Возврат от магазина | «Отрицательный расход» — ломает статистику категории, среднее и медиану | Обратная проводка в ту же категорию, категория честно нетируется |
| Дал в долг другу | Это не расход — деньги не исчезли, изменилась форма актива. В плоской модели выразить нечем | Перевод на счёт-контрагент «Долг: Иван» |
| Трата по кредитке + позже платёж по ней | Двойной счёт: и покупка, и платёж выглядят как расход | Покупка = расход + рост обязательства; платёж = перевод между счётом и обязательством |
| Сплит покупки на 3 категории | Нужна вторая таблица подстрок — то есть уже многопроводочная модель, но кривая | Три расходные проводки в одной транзакции |
| Сверка | Нечего проверять: баланс не выводится из операций, он либо хранится отдельно (и дрейфует), либо считается по типам с исключениями | Баланс = сумма проводок по счёту. Расхождение с реальностью математически локализуемо |
| Чистая стоимость | Хранится отдельно и расходится с операциями | Выводится: активы минус обязательства |
| Покупка инструмента на брокерском | Бессмыслица: деньги «ушли», но не потратились | Обмен денег на позицию |

**Развилка с весами.** Критерии: корректность модели (×5), стоимость обучения пользователя (×5, из блока 2 это главный убийца), стоимость разработки (×2), выразительность для будущих фич — инвестиции, долги, сверка (×4), простота отчётных запросов (×3).

| Вариант | Корректность (×5) | Порог для пользователя (×5) | Стоимость разработки (×2) | Выразительность (×4) | Простота запросов (×3) | Итого |
|---|---|---|---|---|---|---|
| Плоский список + `type` | 1 | 5 | 5 | 1 | 2 | **50** |
| Плоский + `linked_transaction_id` для переводов | 2 | 5 | 4 | 2 | 2 | **57** |
| Двойная запись, видимая в UI (GnuCash/Beancount) | 5 | 1 | 3 | 5 | 5 | **71** |
| **Двойная запись, полностью скрытая от пользователя** | **5** | **5** | **2** | **5** | **5** | **89** |

**Рекомендация: полная двойная запись в домене и в базе, ноль двойной записи в интерфейсе.**

Как именно она скрывается — механика, а не лозунг. В UI существует ровно **четыре глагола**, и каждый из них есть шаблон проводок:

| Глагол в UI | Что видит пользователь | Что происходит в леджере |
|---|---|---|
| **Трата** | сумма, куда (категория), откуда (счёт) | проводка −N на счёте, проводка +N на расходной категории |
| **Доход** | сумма, откуда (источник), куда (счёт) | +N на счёте, −N на доходном источнике |
| **Перевод** | сумма, со счёта, на счёт | −N и +N между двумя счетами; если валюты разные — плюс проводка курсовой разницы |
| **Корректировка** | «на карте на самом деле X» | проводка выравнивания счёта + компенсирующая на служебный счёт «Корректировка» |

Ключевой ход: **категория — атрибут расходной/доходной проводки, а не транзакции.** Отсюда сплиты получаются бесплатно: три проводки в одной транзакции, три категории, без дополнительной таблицы и без специального режима в UI. И отсюда же возвраты работают сами: возврат — транзакция с проводкой противоположного знака в ту же категорию, а пользователь видит строку «Возврат 1 200 ₽ от Ozon».

Что **нельзя** и не нужно скрывать — **существование счетов**. «Карта», «наличные», «вклад» — это не бухгалтерская абстракция, а прожитая реальность. Счёт — единственное понятие двойной записи, которое пользователь уже знает.

Инвариант, который должна защищать сама база: **сумма проводок транзакции в базовой валюте равна нулю**. Это правило Beancount, и оно должно быть выражено ограничением/триггером либо проверкой в агрегате плюс регулярной ревизией, а не «мы аккуратно пишем код».

**Отвергнуто:** плоский список с `linked_transaction_id`. Причина отказа — путь, по которому пошли почти все трекеры, и он даёт худшую двойную запись: связанная пара может рассинхронизироваться (удалили одну сторону), каждый агрегатный запрос обязан знать про исключения по типу, сплиты требуют отдельной таблицы, а сверка остаётся невозможной. Суммарная сложность выходит выше, чем у честной двойной записи, а корректность ниже.

**Отвергнуто:** двойная запись, видимая пользователю. Причина — блок 2, причина 5: продукт умирает на обрыве входа. Бухгалтерская чистота достижима без бухгалтерского словаря.

### 3.4 План счетов для частного лица

Внутри — пять классических типов (Активы, Обязательства, Доходы, Расходы, Капитал). Наружу — то, что человек узнаёт без объяснений:

| Наружу | Внутренний тип | Особенности |
|---|---|---|
| Карта, наличные, счёт | Актив | валюта, признак ликвидности, опционально маска номера |
| Накопительный счёт, вклад | Актив | ставка, дата окончания, признак «не считать в свободных деньгах» |
| Кредитная карта | **Обязательство** | день выписки, день платежа, лимит, беспроцентный период |
| Кредит, рассрочка, ипотека | Обязательство | график платежей, тело и проценты раздельно |
| Долги людям (в обе стороны) | Актив или обязательство | ссылка на человека; при совместных пространствах — на `userId` из Auth |
| Брокерский счёт, ИИС | Актив | держит позиции, а не только деньги; см. ниже |
| Имущество: квартира, авто | Актив | история оценок, а не одна цифра |
| **Начальные остатки** | Капитал | служебный: поглощает стартовый баланс, чтобы книги сходились без ввода истории |
| **Корректировка** | Капитал | служебный: легитимный дом для «не знаю, куда ушло 300 ₽» |
| **Не разнесено** | Расход | служебный: временный дом для черновиков |

Три служебных счёта — это не техническая деталь, а **продуктовое решение, снимающее два барьера входа**: «Начальные остатки» позволяют начать сегодня и не вводить историю за пять лет; «Корректировка» позволяет не врать; «Не разнесено» позволяет записать за 3 секунды.

**Кредитные карты — отдельно, потому что тут все ошибаются.** Кредитка — не «кошелёк с отрицательными деньгами», а обязательство. Из правильной модели бесплатно получается то число, которое человеку реально нужно и которого нет почти нигде: **«долг по последней выписке и дата, до которой его надо закрыть, чтобы не платить проценты»**.

**Инвестиции.** Рекомендация: позиции моделировать как (инструмент, количество, цена приобретения) с отдельным потоком оценок, а не как денежные суммы. В v1 можно не реализовывать, но **схема не должна этому мешать**: проводка обязана уметь нести количество и единицу, а не только деньги. Это ровно то решение, которое невозможно добавить потом без миграции всего леджера.

### 3.5 Транзакции

**Атомарность.** Транзакция — агрегат; проводки не существуют вне него и мутируются только его методами (`INV-DATA-1`). Транзакция, её проводки и outbox-строка пишутся одним `SaveChangesAsync` (`INV-DATA-2`). Для леджера это не стилистика, а корректность: половина проводок — это испорченный баланс.

**Неизменяемость и сторно.** Развилка:

| Модель | Плюс | Минус | Вердикт |
|---|---|---|---|
| Правка всегда разрешена | просто, привычно | ломает закрытые периоды и снапшоты, историю нельзя объяснить | нет |
| Полная неизменяемость с первого дня, любая правка — сторно | идеальный аудит | наказывает за опечатку, требует своего UI отмены, раздувает список | нет |
| **Правка до закрытия периода/сверки, дальше только сторно** | и опечатку исправить можно, и закрытый месяц не поедет | нужен явный барьер и его объяснение в UI | **да** |

Реализация барьера: у транзакции есть состояние проводок `uncleared → cleared → reconciled`, и дата закрытия периода. Правка проводки в состоянии `reconciled` или в закрытом периоде запрещена; вместо неё создаётся сторно со ссылкой `reverses_transaction_id` и компенсирующая запись в текущем периоде.

**Осторожно с soft-delete.** `INV-DATA-4` требует глобальных фильтров на удалённые строки. Для леджера это опасно: «удалённая» проводка, невидимая фильтром, но присутствующая в таблице, — это баланс, который зависит от того, кто спрашивает. Рекомендация: **удаление транзакции пользователем = сторно, а не soft-delete.** Флаг `IsDeleted` из `BaseEntity` остаётся только для административной чистки и никогда не участвует в арифметике баланса. Это отклонение от общего паттерна проекта нужно зафиксировать отдельным ADR.

**Черновики.** Черновик — транзакция с одной проводкой на служебный счёт «Не разнесено» и флагом `needs_review`. Спорный вопрос: влияет ли черновик на баланс? **Да, влияет.** Деньги действительно ушли; если черновик не влияет, баланс врёт, а из блока 2 мы знаем, что врущий баланс — причина отказа. Зато состояние «не разнесено» показывается первоклассным, не осуждающим числом: «не разнесено: 4 операции, 3 120 ₽».

**Идемпотентность записи.** Каждая транзакция получает id на клиенте (см. [6.7](#67-офлайн-и-оптимистичные-обновления)), и эндпоинт записи идемпотентен по этому id. Это одновременно решает дубли при повторной отправке, работу из офлайн-очереди и двойное нажатие кнопки.

### 3.6 Категоризация

**Плоско или иерархически.** Развилка с весами. Критерии: поддерживаемость пользователем (×5), полезность агрегатов (×4), сложность UI (×3), сложность запросов (×2).

| Вариант | Поддерживаемость (×5) | Полезность агрегатов (×4) | Сложность UI (×3) | Сложность запросов (×2) | Итого |
|---|---|---|---|---|---|
| Только плоские категории | 5 | 2 | 5 | 5 | 58 |
| **Две ступени: группа → категория, плюс свободные теги** | **4** | **5** | **4** | **4** | **60** |
| Дерево произвольной глубины | 1 | 5 | 2 | 1 | 33 |
| Только теги, без категорий | 3 | 2 | 4 | 3 | 41 |

**Рекомендация: ровно две ступени плюс теги.** Группа нужна, потому что человек мыслит и «кафе», и «еда вообще»; третий уровень не поддерживается никем и никогда `[вывод]`. Всё, что хочется как третий уровень, — это тег («отпуск», «ремонт», «подарки»), и теги хороши тем, что ортогональны: одна операция может быть и «Продукты», и «#отпуск».

**Ноль категорий по умолчанию.** Это главная рекомендация блока. Механика холодного старта без предустановок:

1. **MCC-коды как основа.** Выписки и уведомления по картам несут четырёхзначный код категории мерчанта (5411 — продуктовые, 5812 — рестораны, 4111 — транспорт). Это готовый, стандартизованный, точный источник — гораздо надёжнее угадывания по тексту «SBERBANK ONL@YN». Таблица MCC → предлагаемое имя категории даёт качественный старт без навязывания.
2. **Мерчант вперёд, категория потом.** Пользователь помнит «Пятёрочка», а не «Продукты питания». Ввод узнаёт мерчанта; категория — следствие.
3. **Категории называет пользователь.** Первые 15–25 операций формируют его собственную таксономию; продукт предлагает имена, но не настаивает.

**Правила автокатегоризации.** Таблица правил с приоритетом: условие (мерчант по нормализованной строке или регулярному выражению, диапазон суммы, счёт, MCC) → действие (категория, теги). Требования: (а) детерминированность — одинаковый вход даёт одинаковый выход; (б) **объяснимость — на любую категоризацию продукт обязан ответить «почему так»** («правило: мерчант содержит ВКУСВИЛЛ»); (в) порог уверенности — выше порога применяем, ниже кладём в Inbox с *подсказкой*, а не с молчаливой догадкой. Молчаливая неверная догадка хуже, чем отсутствие догадки: она портит статистику и подрывает доверие к цифрам, которые пользователь не проверял.

**Почему чужие дефолтные категории не работают.** Три причины: (1) структура потребления культурно специфична — в западных наборах есть «Dining out» и нет «Продукты на неделю в Ашане», есть «Student loans» и нет «Коммуналка + капремонт»; (2) язык — переведённая категория звучит как перевод, и пользователь ей не доверяет; (3) мёртвая категория — это не просто мусор, а активный вред: она разбавляет список выбора при вводе и увеличивает время на разнос, то есть напрямую бьёт в причину отказа №1.

**Отдельное архитектурное решение: категории Eco — свои, не из CategoryApi.** В Planora уже есть сервис категорий (`Services/CategoryApi`, база `planora_category`, `docs/database.md:180`), но он владеет категориями **задач**. Денежные категории имеют другую семантику: знак (расход/доход), бюджетную привязку, группу-роллап, MCC-маппинг. Рекомендация — Eco владеет своими категориями (`INV-OWN-1` это и требует), переиспользуя **визуальный словарь** (иконки, набор цветов) через фронтендовый `frontend/src/lib/icon-map.ts`, и при необходимости хранит необязательную ссылку `planora_category_id` для сцепки «задача со стоимостью».

**Отвергнуто:** единая таксономия на весь Planora через CategoryApi. Причина — общая таксономия навязывает изменения одного домена другому и размывает границу сервисов; плюс «Работа» как категория задачи и «Работа» как источник дохода — разные вещи, а слияние их в одну сущность создаст неустранимую путаницу в UI.

| Модель | Влияние (×5) | Порог входа (×5) | Устойчивость (×4) | Объяснимость (×3) | Итого |
|---|---|---|---|---|---|
| Строгий zero-based (YNAB) | 5 | 1 | 3 | 5 | 57 |
| **Гибкие конверты с переносом остатка + одно производное число** | **4** | **4** | **4** | **5** | **71** |
| Просто лимиты по категориям (Monzo Targets) | 2 | 5 | 4 | 4 | 63 |
| Только прогнозный бюджет из истории | 1 | 5 | 5 | 2 | 56 |

**Рекомендация: гибкие конверты с переносом остатка по умолчанию, плюс ровно одно производное число наружу — «сколько безопасно потратить сегодня».**

Модель данных: период (месяц) × категория → выделено; режим переноса `carry` (остаток переходит) / `reset` (обнуляется) / `carry_negative` (перерасход тоже переходит — для тех, кто хочет честности). Переносить остаток по умолчанию, потому что обнуление наказывает за экономию: человек, который сэкономил в январе, не должен «терять» это в феврале.

Формула «безопасно сегодня»: (сумма нераспределённых остатков гибких конвертов на остаток периода − известные предстоящие обязательные платежи в этом периоде) ÷ число оставшихся дней. Число обязано раскрываться по нажатию в три слагаемых — иначе это магия, а магии в деньгах не доверяют.

**Отвергнуто:** строгий zero-based по умолчанию. Причина — крупнейший обрыв входа в категории (см. 1.1 и блок 2, причина 5). Оставить как опциональный «строгий режим» для тех, кто уже знает метод YNAB: у них он даёт лучший результат, и отбирать его нельзя.

**Отвергнуто:** блокирующее предупреждение «ты не можешь себе это позволить» в момент траты. Причина — патернализм и прямой путь к избеганию приложения (блок 2, причина 2).

### 3.8 Повторяющиеся операции и прогноз

**Модель повторения:** правило повторения (подмножество RRULE: каждые N дней/недель/месяцев, «последний рабочий день месяца», «5-е число»), шаблон проводок, следующая дата, флаг `auto_post`, характер суммы `fixed` или `estimated`.

**Автопостинг только для фиксированных сумм.** Подписка за 399 ₽ — можно проводить автоматически. Коммуналка «примерно 6 000» — нельзя: автопостинг оценочной суммы означает, что баланс становится приблизительным, а это нарушает главное требование к балансу. Оценочные повторения живут как «ожидается ~6 000 ₽ около 10-го» и участвуют в прогнозе, но не в балансе.

**Детекция повторений из истории:** один и тот же нормализованный мерчант, сумма в пределах ±10%, интервалы, кластеризующиеся вокруг 7 / 14 / 28–31 / 365 дней, минимум 3 наблюдения. Результат — не автоматическое создание, а предложение: «похоже, это подписка — 399 ₽ каждый месяц с марта. Отслеживать?»

**Прогноз денежного потока.** Строится как сумма: (а) известные повторения, (б) выделенное по конвертам на остаток периода, (в) медиана по нераспределённым переменным категориям за последние 3–6 месяцев. Горизонты 3 / 6 / 12 месяцев.

**Показывать полосой, а не линией.** Одна линия прогноза — это ложь о дисперсии. Полоса p25–p75 по историческому разбросу честна и при этом читается лучше: пользователь видит не «будет 142 000», а «скорее всего между 118 000 и 156 000». Разброс — это и есть содержание прогноза.

**Годовая стоимость — самый дешёвый сильный инсайт продукта.** 399 ₽/мес = 4 788 ₽/год. 250 ₽ кофе пять раз в неделю = 65 000 ₽/год. Это одна операция умножения и одна строка в UI, и она меняет решения сильнее, чем любая диаграмма.

### 3.9 Периоды, закрытие, снапшоты

**Сначала честная арифметика объёмов, потому что здесь принято повторять догму без счёта.**

Активный пользователь: 10 операций в день = 3 650 транзакций в год, при среднем 2,5 проводки на транзакцию ≈ 9 100 проводок в год. За 10 лет: **≈ 36 500 транзакций и ≈ 91 000 проводок**. При ~120 байтах на строку проводки это **≈ 11 МБ данных плюс индексы, порядка 20–25 МБ на пользователя за десятилетие** `[вывод, расчёт мой]`.

Для PostgreSQL 100 000 строк с индексом по `(user_id, booked_on)` — это единицы миллисекунд. **Вывод, противоречащий стандартной догме: для одного пользователя агрегация «с нуля» остаётся приемлемой на протяжении десятилетия.** Предварительная агрегация нужна не из-за объёма.

**Тогда зачем снапшоты.** Три настоящие причины:

1. **Неизменность закрытых периодов.** Закрытый месяц должен давать один и тот же ответ всегда — даже если позже уточнился курс, переименовалась категория или появилась ретроспективная корректировка. Это требование к продукту, а не к производительности.
2. **Размер ответа, а не время запроса.** «Чистая стоимость по месяцам за 10 лет» — это 120 точек; посчитать легко, но собирать их из 91 000 проводок на каждый заход мобильного клиента по медленной сети расточительно, и платит за это TTFB (а он у нас на SSR из-за `force-dynamic`).
3. **Исторические оценки.** «Как выглядела моя чистая стоимость три года назад» требует оценок активов и курсов **того времени**, а не сегодняшних. Без снапшота это восстановимо только если хранить всю историю оценок — а значит снапшот всё равно нужен, просто в другом виде.

**Рекомендация:** снапшот периода `(пользователь, период, счёт|категория) → входящий остаток, приход, расход, исходящий остаток`, материализуемый при закрытии периода; плюс снапшот остатков по счетам на конец каждого месяца. Снапшот — **производная величина, воспроизводимая из проводок**, и фоновая задача обязана периодически пересчитывать и сверять: расхождение — это алерт, а не повод тихо перезаписать.

**Отвергнуто:** материализованные представления PostgreSQL. Причина — `REFRESH` блокирует либо требует `CONCURRENTLY` с уникальным индексом, обновляется целиком, и не даёт того, что нужно на самом деле (иммутабельность закрытого периода). Снапшот как обычная таблица с явной семантикой лучше.

**Отвергнуто:** отказ от снапшотов «потому что данных мало». Причина — данных действительно мало, но закрытый период обязан быть неизменным, и это не вопрос производительности.

**Партиционирование** (по `booked_on`, RANGE, погодично) — только когда одна таблица проводок перевалит за ~50–100 млн строк, то есть примерно на 500–1 000 активных пользователей-десятилетиях. До этого партиционирование стоит дороже, чем даёт: растёт время планирования, индексы дробятся, а выгода нулевая.

### 3.10 Импорт

**Реальность рынка, а не теория.** В российских банках практически нет OFX и QIF; есть CSV, XLSX и PDF. Кодировка — нередко windows-1251; десятичный разделитель — запятая; формат даты — свой у каждого; порядок колонок — свой у каждого; **стабильного идентификатора операции обычно нет**.

**Идемпотентность через хеш строки.** Ключ дедупликации: `sha256(account_id ‖ booked_on ‖ amount_minor ‖ normalized_description ‖ external_id?)`. Хранится в `import_row_hash` с уникальным индексом по `(user_id, import_row_hash)`. Повторная загрузка того же файла — ноль новых строк, и это должно быть видно пользователю: «в файле 214 операций, 212 уже были, добавлено 2».

**Почему хеш, а не внешний id.** Внешнего id обычно нет. Когда он есть — использовать его как часть хеша, не вместо: банк может переиспользовать номера операций между выписками `[вывод]`.

**Близкие дубли — спрашивать, не сливать.** Та же сумма в пределах ±3 дней и похожий мерчант → флаг «возможно дубль» и вопрос. Автоматическое слияние недопустимо: две одинаковые покупки кофе в один день — норма жизни, а не ошибка.

**Профили импорта.** Пользователь один раз сопоставляет колонки («дата — 1-я, сумма — 4-я, описание — 3-я, минус означает расход»), и профиль сохраняется на банк: `import_profile(bank, column_map, encoding, date_format, decimal_separator, sign_convention)`. Второй импорт из того же банка — ноль вопросов. Это ровно то место, где ручная работа один раз превращается в автоматизацию навсегда.

**PDF в v1 — нет.** Причина в [«Что я НЕ рекомендую»](#что-я-не-рекомендую-делать-и-почему).

### 3.11 Сверка с реальностью

**Почему без сверки цифры перестают быть правдой.** Любой ручной или полуавтоматический учёт расходится с действительностью: забытая покупка, комиссия, кэшбэк, округление в банке. Расхождение накапливается молча, и через 3–4 недели пользователь замечает, что приложение показывает не то, что карта. С этого момента все выводы приложения обесцениваются сразу и целиком — потому что доверие к производным числам держится на доверии к остатку.

**Модель.** Проводка имеет состояние: `uncleared` (записана пользователем) → `cleared` (подтверждена выпиской или сверкой) → `reconciled` (заперта сверкой, правка только сторно). Сверка: `reconciliation(account, as_of, statement_balance_minor, our_balance_minor, diff_minor, resolution)`.

**Ритуал на 20 секунд.** Один вопрос — «сколько сейчас реально на карте?». Одно поле. Если разница нулевая — подтверждение и запирание периода. Если нет — три варианта, в этом порядке:

1. **Найти пропущенное**: список кандидатов — операции, которые продукт ожидал, но не видит (ненаступившие повторения, незакрытые черновики, похожие суммы в других счетах).
2. **Создать корректировку**: одна кнопка, проводка на служебный счёт «Корректировка». Это честный ответ «не знаю», и он лучше любой подгонки.
3. **Оставить как есть**: тоже допустимо, но тогда сверка не запирает период.

**Отвергнуто:** автоматическая подгонка остатка без явной корректирующей проводки. Причина — это ровно тот механизм, из-за которого баланс «сам собой» становится неверифицируемым: сумма проводок больше не равна остатку, и инвариант потерян.

## Блок 4 — «Экономика», а не «экономия»

Разница в одном: экономия отвечает на «как потратить меньше», экономика — на «как устроена моя система и что в ней изменится, если я сделаю X». Второе требует других метрик.

### 4.1 Чистая стоимость и её разложение

**Формула:** сумма активов минус сумма обязательств на дату, где активы в иностранных валютах и неденежные активы переоценены по курсу и оценке **на эту дату** (см. правило 2 в [3.2](#32-мультивалютность)).

**Данные:** остатки счетов (выводятся из проводок), история оценок неденежных активов, курсы на дату.

**Как показать, чтобы меняло поведение.** Не числом. Числом это показывают все, и это не работает: чистая стоимость меняется по причинам, которые человек не контролирует, и потому её рост не подкрепляет поведение, а её падение демотивирует. Показывать нужно **разложение дельты** — водопадом:

```
Было 3 месяца назад ........ 1 840 000
  + отложено ..................... 96 000   ← это ты
  − потрачено сверх дохода ....... −12 000   ← это ты
  + переоценка активов ........... +31 000   ← это рынок
  + курсовая разница .............. +8 400   ← это курс
Стало ...................... 1 963 400
```

Смысл: **разделить «я стал богаче, потому что откладывал» и «я стал богаче, потому что вырос курс».** Первое — заслуга и подкрепление, второе — шум. Ни один известный мне массовый продукт не показывает это разделение явно `[вывод]`, а это самое честное, что финансовое приложение может сказать человеку.

### 4.2 Реальная динамика с поправкой на инфляцию

**Формула:** дефлирование к базовому месяцу по индексу потребительских цен: `реальная величина = номинальная × (ИПЦ базового месяца / ИПЦ месяца наблюдения)`.

**Данные:** месячный ряд ИПЦ (Росстат для РФ). Публикуется с задержкой — значит последние 1–2 месяца показываются как номинальные с явной пометкой, а не экстраполируются.

**Как показать:** две линии на одном графике — номинальная тонкая, реальная жирная. Единственная цель: объяснить чувство «денег столько же, а хватает меньше».

**И более сильная версия — личная инфляция.** ИПЦ описывает среднюю корзину, а не корзину пользователя. Если у нас есть повторяющиеся покупки одних и тех же позиций или хотя бы у одних и тех же мерчантов, можно построить **индекс цен пользователя**: как изменилась стоимость его собственного набора при том же количестве. Результат — «твоя личная инфляция 11,4% против официальной 8,2%, и сильнее всего для тебя подорожали: кофе +34%, коммуналка +19%». Это знание невозможно получить никаким другим способом, и оно немедленно объясняет ощущение. Требует детализации до позиций (чеки) — поэтому это флагман второй версии, но **схема обязана допускать позиции внутри операции с самого начала**.

### 4.3 Burn rate и runway

**Формула:** `burn = медиана полного оттока за последние 3 полных месяца`, где отток считается без переводов между своими счетами и без разовых выбросов выше 90-го процентиля (они искажают медиану месяца, в который попали). `runway = ликвидные активы ÷ burn`.

**Данные:** проводки, признак ликвидности счёта, классификация операций как разовых.

**Как показать: датой, а не числом.** «Runway 7,4 месяца» — абстракция. «Если доход исчезнет сегодня, деньги закончатся 26 апреля 2027» — конкретное, проверяемое, запоминающееся утверждение. Дата активирует планирование; число активирует кивок.

Второй ход: показать **производную** — «месяц назад эта дата была 12 апреля, ты отодвинул её на две недели». Движение границы свободы — самое сильное подкрепление, какое можно придумать в деньгах `[вывод]`.

### 4.4 Норма сбережений и горизонт свободы

**Формула, наивная:** `(доход − расход) / доход` за период. **Формула, честная:** `(изменение чистой стоимости, очищенное от переоценки и курса) / доход` — потому что «сэкономил» и «деньги остались лежать на счёте» это одно и то же, а «сэкономил и купил актив» наивной формулой считается как расход.

**Связь с горизонтом.** Отношение «норма сбережений → годы до финансовой независимости» нелинейно и это главный нетривиальный факт личной экономики: при норме 10% горизонт — десятилетия, при 50% — около десятка лет. Опора: правило 4% Уильяма Бенджена (Journal of Financial Planning, 1994), подтверждённое и популяризованное Trinity study (Cooley, Hubbard, Walz, 1998); отсюда «правило 25×» — необходимый капитал равен 25 годовым расходам ([Wikipedia: 4% rule](https://en.wikipedia.org/wiki/4%_Rule), [The Poor Swiss о Trinity study](https://thepoorswiss.com/trinity-study/)).

**Обязательная оговорка в самом UI:** правило 4% выведено на исторических данных рынка США за 30-летние периоды начиная с 1926 года. Это не обещание и не применимо механически к рублёвым сбережениям. Показывать как **чувствительность, а не как предсказание**: «+1 п.п. к норме сбережений сдвигает горизонт на N месяцев» — это утверждение о структуре, и оно верно независимо от того, угадана ли доходность.

### 4.5 Стоимость покупки в единицах жизни

**Формула:** `реальная часовая ставка = чистый доход / (рабочие часы + дорога + сопутствующие траты и время)`. Концепция и методика — из «Your Money or Your Life» (Vicki Robin, Joe Dominguez): смысл в том, что человек продаёт не труд, а часы жизни, и настоящая ставка всегда ниже номинальной.

**Данные:** чистый доход (из леджера), рабочие часы и дорога (вводит пользователь один раз).

**Как показать, не превратившись в моралиста.** Не текстом «ты потратил 3 часа жизни на кофе» — это осуждение, и оно попадает прямо в причину отказа №2. Показывать как **переключатель единиц измерения**: одна кнопка меняет всю страницу из ₽ в «часы работы» / «дни свободы» / «% месячного потока». Как °C ↔ °F. Смена единиц — это любопытство; тот же факт в виде реплики — это упрёк. Разница только в подаче, и она определяет, останется пользователь или нет.

### 4.6 Альтернативная стоимость и стоимость владения

**Альтернативная стоимость:** та же сумма при заданной ставке за N лет. Показывать сдержанно и только по запросу: агрессивная подача («эти 90 000 могли бы стать 210 000!») — это манипуляция, и она обесценивает инструмент.

**Стоимость владения (TCO):** для активов считать полную стоимость, а не цену. Автомобиль: топливо + страховка + обслуживание + шины + налог + амортизация, приведённое к рублю на километр. Это число человек не знает почти никогда, и оно меняет решения радикальнее любого бюджета. Данные берутся из категорий, привязанных к активу — то есть **актив должен уметь быть измерением расходов**, а не только строкой в балансе. Это требование к схеме.

### 4.7 Годовая, а не месячная стоимость

Уже описано в [3.8](#38-повторяющиеся-операции-и-прогноз); повторяю здесь потому, что это метрика, а не фича: **каждая повторяющаяся трата показывается в годовом выражении рядом с месячным.** Продукт обязан один раз в месяц показывать сумму всех подписок за год и список неиспользуемых — это механика Emma, и она работает потому, что несёт одно конкретное действие.

### 4.8 Прогноз и сценарии «а что если»

**Прогноз** — в [3.8](#38-повторяющиеся-операции-и-прогноз): полоса p25–p75, не линия.

**Сценарий как объект данных, а не как калькулятор.** `scenario(name, deltas[])`, где дельта — это «доход ×0 с апреля», «расходы −20%», «разовая трата 500 000 в июне», «+12 000 к платежу по кредиту». Сценарий сохраняется, к нему возвращаются, его сравнивают с базой.

**Как показать:** две полосы на одном полотне — базовая серым, сценарная акцентом, и **одно число разницы**, сформулированное как срок, а не как сумма: «горизонт свободы: +8 месяцев». Ключевое требование к отклику: изменение параметра сценария обновляет картинку за ≤ 200 мс, иначе исследование превращается в ожидание и пользователь перестаёт играть. Это значит, что прогноз должен считаться на клиенте из компактного предрасчитанного набора, а не запросом на сервер за каждый сдвиг ползунка.

### 4.9 Личный P&L и личный баланс по-человечески

Бухгалтерские формы наружу не показывать. Показывать теми же двумя отчётами, но словами:

> **Год.** Пришло 3 240 000. Ушло 2 610 000. Осталось 630 000.
> Из них 420 000 переведено в накопления, 210 000 просто лежит на счетах.
> Самая крупная группа расходов — жильё, 780 000 (30%). Год назад было 26%.

Требование: любое число в такой сводке — **ссылка**, ведущая в список операций, из которых оно состоит. Число, которое нельзя развернуть до операций, в финансовом продукте не имеет права существовать: именно неразворачиваемые числа порождают недоверие ко всему остальному.

### 4.10 Сезонность, тренды, аномалии

**Сезонность:** сравнение месяца с тем же месяцем прошлого года, а не с предыдущим. Декабрь всегда дороже ноября, и сравнение с ноябрём производит ложную тревогу.

**Аномалии:** робастный z-score по категории — `(значение − медиана) / (1,4826 × MAD)` вместо среднего и σ, потому что среднее и стандартное отклонение сами разрушаются одним выбросом. Порог — 3.

**И главное требование: аномалия обязана называть причину.** «Этот месяц не такой, как обычно» без объяснения — это шум и тревога. Правильная формулировка: «на 18 400 ₽ больше обычного; 82% разницы — одна операция «Авиабилеты» 15 100 ₽; без неё месяц в норме». Продукт обязан уметь разложить отклонение на вклад отдельных операций и назвать те, что дают >50% разницы. Аномалия без атрибуции не выпускается.

### 4.11 Сводка: одно число наружу

Из блока 1 (Whoop, Oura) и блока 2 (перегруз = отказ) следует: главный экран должен нести **одно первичное число про сейчас** и **одно про траекторию**. Кандидаты и вердикт:

| Кандидат | За | Против | Вердикт |
|---|---|---|---|
| Остаток на счетах | понятен всем | ничего не значит: 80 000 за день до аренды и после — разные вещи | нет |
| Потрачено за месяц | привычно | ретроспективно, порождает вину | нет |
| **Безопасно потратить сегодня** | отвечает на реальный вопрос, выводимо, действенно | требует бюджета и повторений | **да, первичное** |
| **Чистая стоимость и её дельта** | единственная метрика «как я живу в целом» | медленная, не про сегодня | **да, вторичное** |
| Скор финансового здоровья 0–100 | одно число, красиво | не выводимо из данных пользователя без нормативов, то есть врёт | нет, см. запреты |

Общий знаменатель, который стоит выписать отдельно: **у всех этих продуктов задержка отклика воспринимается как ноль.** Это не украшение, это фундамент. Оптимистичное обновление обязательно: запись транзакции отображается мгновенно, сеть догоняет.

### 5.2 Информационная архитектура

Три уровня и одно постоянное действие.

**L0 — «Сейчас».** Отвечает на три вопроса за ≤ 5 секунд: сколько у меня есть, сколько можно тратить, что изменилось. Состав: одно первичное число («безопасно сегодня»), одно вторичное (чистая стоимость + дельта), **одно конкретное предложение**, выведенное из данных, и «Кривая правды» (см. [5.12](#512-пять-интерфейсных-идей-которых-нет-ни-у-кого)). Всё. Ни списка операций, ни круговой диаграммы, ни шести карточек-метрик.

**L1 — «Поток».** Месяц: куда идут деньги. Конверты с прогрессом, разбор потока (Sankey) по запросу, календарная теплокарта ритма, аномалии с атрибуцией. Здесь живут отчёты, и каждый заканчивается действием.

**L2 — «Правда».** Счета, остатки, сверка, история операций, импорт, правила. Это «машинное отделение»: сюда заходят редко, но здесь всё должно быть предельно точным и полным.

**Постоянное действие** — захват операции. Доступен с любого уровня, одним жестом, без потери контекста: возвращает туда, откуда открыли.

**Переход от общего к частному — по одному правилу: любое число разворачивается в операции, из которых состоит.** Не «есть отдельная страница транзакций», а «нажми на 780 000 — увидишь 46 операций, которые его образуют». Это и навигация, и механизм доверия одновременно.

**Отвергнуто:** дашборд из 6–8 карточек-метрик (индустриальный стандарт). Причина — перегруз и отсутствие приоритета: когда всё важно, не важно ничто, а пользователь уходит с ощущением «посмотрел и ничего не понял» (блок 2, причина 4).

### 5.3 Ввод транзакции

**Целевые метрики трения.** Измеряем в касаниях и секундах, для типовой траты на телефоне, при открытом приложении:

| Способ | Касаний | Секунд (цель) | Покрытие операций |
|---|---|---|---|
| **Повтор недавней** (долгое нажатие на чип мерчанта → подтвердить) | **1** | **≤ 1,0** | ~40–50% (повторяющиеся бытовые траты) `[оценка]` |
| **Естественный ввод** («кофе 350» + Enter) | **2** | **≤ 3,0** | ~80% |
| Голос (диктовка в тот же парсер) | 2 | ≤ 4,0 | руки заняты |
| Фото чека (снял — разобрали позже) | 2 | ≤ 2,5 до записи | там, где сумма неизвестна |
| Полная форма (сплит, перевод, валюта) | 5–8 | 15–25 | ~5% |
| **Для сравнения: типичный трекер** | 5–8 | 15–30 | 100% |

Три секунды и два касания — это и есть весь замысел. Разберём, как именно.

**Грамматика естественного ввода.** Одна строка, порядок токенов свободный:

```
[сумма] [валюта?] [текст-мерчант] [@счёт] [#категория] [слово-дата]
```

Правила разбора:

- Сумма — **первый числовой токен**; «350», «350.50», «350,50» равнозначны; «350к» = 350 000; «1.2к» = 1 200.
- Расход — **умолчание**; доход требует явного «+» или слова «получил/зарплата». Асимметрия оправдана: расходов в 10–20 раз больше.
- Валюта — символ или код (`$`, `€`, `usd`); без неё — валюта счёта.
- `@` — счёт, `#` — категория; оба с автодополнением и оба необязательны.
- Слова-даты: «вчера», «в пятницу», «12-го», «позавчера». Без них — сегодня.
- Остаток строки — мерчант/описание, по нему ищется правило и предсказывается категория.
- **Разбор показывается по мере набора** отдельной строкой-«эхом»: `350 ₽ · Кофе · Продукты · Карта Тинькофф · сегодня`. Пользователь видит, как его понимают, и это снимает главный страх свободного ввода — «а оно правильно поняло?».

**Повтор недавней операции — настоящий рекорд скорости, и его почти никто не делает.** Механика: под строкой ввода — ряд чипов последних/частых мерчантов с типичной суммой (`Пятёрочка 1 240`). Одно нажатие создаёт операцию с медианной суммой и категорией из истории; долгое нажатие открывает правку суммы. Работает потому, что реальная жизнь **повторяется**: одни и те же 10–15 мерчантов дают большую часть операций.

**Фото чека — сначала запись, потом разбор.** Снимок создаёт черновик немедленно (сумма неизвестна, счёт по умолчанию), попадает в Inbox, распознаётся асинхронно. **Никогда не блокировать пользователя на OCR.** Если распознавание не удалось — операция всё равно записана, и это главное.

**Голос — тот же парсер, а не отдельный поток.** Диктовка даёт текст, текст идёт в ту же грамматику. Ни отдельного экрана, ни отдельной логики.

**Почему остальные не смогли.** Продукты с банковской агрегацией (Monarch, Copilot, Monzo) оптимизировали **ноль ввода**, поэтому качественного ручного ввода у них нет — он им был не нужен. Продукты с ручным вводом (Monefy, CoinKeeper) сделали ввод *приятным* (перетаскивание монет), но не *быстрым*, и их модель не выражает переводы и возвраты. **Пустая ниша ровно между: быстрый ввод при корректной модели.**

**Отвергнуто:** пошаговый ввод (сумма → категория → счёт → сохранить) как основной путь. Причина — 5+ касаний, то есть прямое попадание в главную причину отказа. Остаётся как полная форма для 5% сложных операций.

**Отвергнуто:** ввод через диалог с ИИ. Причина — недетерминированность в деньгах разрушает доверие, задержка модели больше целевых 3 секунд, а грамматика справляется без неё. LLM полезна в другом месте: как *подсказчик* категории и нормализатор мерчанта в фоне.

### 5.4 Визуализация: что работает и что врёт

| Тип | Работает для | Врёт / когда не использовать | Вердикт для Eco |
|---|---|---|---|
| **Круговая / кольцевая** | доля 2–4 крупных частей | человек плохо сравнивает углы; при >5 секторах читается хуже отсортированных полос; никогда не показывает изменение | только для ≤4 частей, иначе полосы |
| **Sankey (поток)** | разовый разбор «куда всё ушло» за месяц/год; популярен в FI-сообществе ([Get Rich Slowly](https://www.getrichslowly.org/sankey-diagrams/), [ProjectionLab](https://projectionlab.com/financial-terms/sankey-cash-flow-diagram)) | нечитаем на ширине 390 px; не годится как ежедневный вид; скрывает динамику | отдельный экран «Разбор», с зумом, не на главной |
| **Календарная теплокарта** | ритм: выходные, дни зарплаты, «дорогие» дни | врёт при неперцептивной шкале; при цветах «зелёный–красный» превращается в календарь вины | да, шкала — монотонная по светлоте (OKLCH) |
| **Водопад** | разложение дельты чистой стоимости на причины | бесполезен без честной атрибуции слагаемых | да, **главный график продукта** для «почему изменилось» |
| **Спарклайн в строке** | тренд рядом с числом, без затрат места (Тафти) | не показывает масштаб — обязателен подпись-максимум | да, везде |
| **Кольцо прогресса** | доля израсходованного конверта | превращается в оценку, если краснеет | да, без красного |
| **Столбики с линией нормы** | «этот месяц против обычного» | абсолютные столбики без нормы не несут смысла | да, норма обязательна |
| **Линия прогноза** | — | **всегда врёт**: изображает единственный исход | заменить полосой p25–p75 |
| **Стопка площадей по категориям** | суммарная динамика | врёт про отдельные серии: у каждой плывёт базовая линия | заменить малыми кратными (small multiples) |
| **3D, спидометры, «гейджи»** | ничего | искажают, занимают место | нет |

**Что анимировать, а что нет.** Анимируется: переход значения (число → число), появление элемента, который пользователь только что создал, расширение полосы прогноза при увеличении горизонта. Не анимируется: перерисовка осей при смене периода без общей точки привязки, «прорисовка» линии графика при каждом заходе (очаровательно один раз, раздражает на двадцатый), переупорядочивание списка на каждое нажатие клавиши.

**Развилка: чем рисовать.** Критерии: размер бандла (×4, `force-dynamic` уже платит за SSR), контроль над видом (×4, у нас свой визуальный язык), скорость разработки (×3), совместимость с CSP без `unsafe-inline`/`unsafe-eval` (×5, ADR-0006 запрещает `unsafe-inline`), доступность и семантика (×3).

| Вариант | Бандл (×4) | Контроль (×4) | Скорость (×3) | CSP (×5) | A11y (×3) | Итого |
|---|---|---|---|---|---|---|
| **Свой SVG + framer-motion (уже в бандле)** | **5** | **5** | **2** | **5** | **5** | **86** |
| Recharts | 2 | 3 | 5 | 4 | 3 | 64 |
| visx (набор примитивов d3) | 3 | 5 | 4 | 4 | 4 | 76 |
| Полный d3 | 2 | 5 | 3 | 4 | 3 | 66 |
| Three.js (уже есть в проекте) | 4 | 5 | 1 | 5 | 1 | 67 |

**Рекомендация: собственные SVG-компоненты на framer-motion, без новой зависимости.** Графиков в продукте немного и они нестандартные (водопад с атрибуцией, полоса прогноза, «Кривая правды»); библиотеки общего назначения придётся переопределять целиком, а это дороже, чем нарисовать нужное. SVG даёт полный контроль над типографикой чисел внутри графика — а в финансовом продукте подписи осей это тоже деньги, и они обязаны подчиняться правилам из [5.7](#57-типографика-чисел).

**Отвергнуто:** Recharts. Причина — самый быстрый старт, но навязывает свой вид, свои отступы и свою типографику; кастомизация под наш язык съедает выигрыш, а размер добавляется навсегда.

**Отвергнуто:** Three.js для графиков, хотя он уже в бандле. Причина — ноль доступности (canvas/WebGL не имеет семантики), невозможность выделить и скопировать число, нулевая польза от 3D в деньгах. WebGL в проекте остаётся ровно там, где он уместен: декоративный фон.

| Празднование (конфетти) | 0,58–0,9 с | существующий `celebration.tsx` | **Только на значимых вехах**, см. [5.6](#56-тон-и-эмоция) |

Жёсткие запреты — из принципов, уже записанных в `animations.ts:5`–`:9`: только `transform` и `opacity`; никаких `filter`/`blur`; никаких теней в hover-анимациях; никакого `transition: all`.

**`prefers-reduced-motion`.** Проект уже сжимает все CSS-анимации до 0,01 мс и глушит framer-motion глобально (`globals.css:490`–`:502`). Для Eco дополнительно: числа меняются мгновенно (без роллера), графики появляются без прорисовки, но **смена состояния остаётся видимой** через мгновенный кроссфейд — потому что для финансового интерфейса «число молча стало другим» опаснее, чем лишняя анимация.

**Где движение вредит.** Задержка коммита ради анимации — недопустима: сначала запись, потом анимация. Анимация при загрузке страницы, задерживающая появление главного числа, — недопустима. Анимация, повторяющаяся на каждом переключении вкладки, — недопустима.

### 5.6 Тон и эмоция

**Как показать перерасход без чувства вины.** Формула из трёх частей: **факт → следствие → выбор.** Ни оценки, ни восклицания, ни цвета тревоги.

Плохо (так делают почти все):

> ⚠️ Перерасход! Вы превысили бюджет «Еда» на 4 300 ₽ (117%)

Хорошо:

> Еда: 29 300 из 25 000. Осталось 11 дней.
> Твой обычный темп в этой категории — 850 ₽/день.
> → Перенести 4 000 ₽ из «Развлечения» · → Поднять лимит · → Оставить как есть

Разница не косметическая. Первый вариант сообщает «ты плохой» и предлагает ноль действий. Второй сообщает состояние системы и три способа его изменить — включая «ничего не делать», что снимает принуждение.

**Словарь. Не используем никогда:** «перерасход», «превышение», «должен», «нельзя», «ошибка», «плохо», восклицательный знак в отчётах, эмодзи с отрицательной эмоцией. **Используем:** «осталось», «обычно ты», «хватит на», «можно», «если», «было / стало».

**Как отпраздновать без инфантильности.** В проекте уже есть `frontend/src/components/animated/celebration.tsx` — конфетти на 18 частиц, 0,58–0,9 с, два варианта (экран/карточка). Правило для Eco: **празднование — редкое событие, привязанное к вехе, а не к действию.** Допустимые поводы: первый закрытый месяц; первый пустой Inbox; runway впервые перевалил за 6 месяцев; закрыт кредит; норма сбережений впервые выше 20% три месяца подряд. Недопустимо: празднование записи операции (обесценивает механизм за неделю), ежедневный стрик, «ты молодец, что открыл приложение».

**Как выглядит уважение к пользователю в интерфейсе про деньги.** Четыре проверяемых правила:

1. **Ни одно число не скрыто, если его можно вывести из данных пользователя.** Никаких «доступно в Pro».
2. **Любое число разворачивается до операций.** Нет разворачивания — нет права на существование.
3. **Продукт не догадывается молча.** Автокатегоризация показывает, что она сделала, и почему.
4. **Необратимое действие не делается лёгким.** Удаление счёта с историей, закрытие периода, применение правила ко всей истории — с подтверждением и с явным перечислением последствий («правило затронет 143 операции с марта 2024»).

### 5.7 Типографика чисел

Это самый недооценённый раздел финансового дизайна. Числа — это контент, а не подпись.

**Табличные цифры — обязательны** везде, где числа стоят в колонку или меняются на месте. Без `tnum` цифры имеют разную ширину, колонка «дышит», а меняющееся число дрожит. `[требует проверки]`: поддерживает ли Plus Jakarta Sans фичу `tnum` — метод проверки в [0.5](#05-дыры-которые-eco-обнажит), пункт 6. **План Б, если не поддерживает:** (а) подключить один дополнительный шрифт только для цифр — стоимость ~15–25 КБ на подмножество `0-9 . , − ₽ $ €` и это оправданная цена; (б) либо фиксированная ширина цифрового глифа через контейнер с `ch`-шириной и выравниванием вправо. Вариант (а) лучше: он решает проблему полностью и в одном месте.

**Иерархия размеров.** Первичная сумма экрана: 32–40 px, вес 700–800, трекинг −0,02em (крупные цифры визуально расползаются, отрицательный трекинг это компенсирует). Сумма в списке операций: 15–16 px, вес 600. Подписи осей: 11–12 px, вес 500, приглушённый цвет.

**Копейки.** Показываются **только** на самой операции и на экране сверки. В любом агрегате — целые рубли: копейки в годовой сумме 2 610 000 ₽ — это визуальный шум, отнимающий внимание у значащих разрядов. Когда копейки показываются, они идут на 60–65% размера основной цифры, с прозрачностью 0,6–0,7, **по той же базовой линии** (не надстрочно): надстрочные копейки — приём ценников, и он в учётном интерфейсе читается как реклама.

**Разделители.** Разряды — **узкий неразрывный пробел** (U+202F), а не запятая и не точка: это русская типографическая норма, и запятая в русском тексте конфликтует с десятичным разделителем. Десятичный разделитель — запятая. Валюта — символ **после** суммы, через неразрывный пробел: `12 345 ₽`. Символ валюты — 70–75% размера, приглушённый: он идентификатор, а не значение.

**Отрицательные значения.** Три правила:

1. Минус — **типографский** U+2212 (−), а не дефис: дефис в табличных цифрах слишком короткий и теряется.
2. **Направление кодируется не только минусом.** В списках — раздельные колонки или позиция; в сводках — слова «пришло / ушло». Одинокий минус перед числом слишком легко пропустить при быстром просмотре, а цена ошибки здесь — неверно понятый баланс.
3. **Скобки бухгалтерского стиля — отвергнуты.** Причина: непрофессионалу `(12 345)` не читается как отрицательное значение, это чистая конвенция отрасли, требующая обучения.

**Ноль и пустота — разные вещи.** «Ничего не происходило» — это тире «—». «Ровно ноль» — это `0 ₽`. Смешивать нельзя: пустая категория и категория, где приход равен расходу, — разные факты.

**Выравнивание.** Все суммы — по правому краю, по разрядам. Заголовок колонки — тоже по правому краю. Это делает сравнение сумм в списке физически возможным без чтения каждой.

### 5.8 Цвет

**Почему «красный = плохо, зелёный = хорошо» — ловушка.** Четыре причины, каждая достаточна сама по себе:

1. **Морализация.** Красный превращает каждую трату в порицание и создаёт ту самую павловскую связку из блока 2, причины 2. Расход — не аварийное состояние; это то, ради чего существуют деньги.
2. **Доступность.** Красно-зелёная дефицитность зрения распространена среди мужчин в районе 8%, и для этих пользователей главный семантический канал интерфейса просто отсутствует. WCAG 1.4.1 прямо запрещает кодировать смысл одним цветом.
3. **Двойная перегруженность значения.** В финансах красный уже означает одновременно «направление вниз» и «убыток». Одна и та же пара цветов несёт противоречивые смыслы: `−20 000 ₽` на брокерском счёте — плохо; `−20 000 ₽` на продуктах — это вторник.
4. **Информационная бедность.** Цвет, потраченный на «хорошо/плохо», больше нельзя потратить на «что это за категория» или «на что смотреть сейчас» — то есть на настоящую работу.

**Что вместо.** Три роли цвета, строго разделённые:

| Роль | Средство | Правило |
|---|---|---|
| **Значение (суммы)** | цвет текста (near-black в светлой теме) | Все суммы одного цвета. Направление — типографикой и позицией |
| **Идентичность (категории)** | перцептивно ровная палитра в OKLCH: одинаковая светлота L, разный тон H | Ни одна категория не выглядит «важнее». 8–12 тонов достаточно; дальше — паттерны заливки |
| **Внимание (одно место)** | один акцент — существующий `#0ea5e9` либо near-black primary (`design-tokens.ts:33`, `:49`) | Один акцент на экран. Два акцента = ноль акцентов |
| **Отклонение / тревога** | контраст и вес, а не тон | Если дивергирующая шкала неизбежна («выше/ниже нормы») — **синий ↔ янтарный**, не красный ↔ зелёный |

Хорошая новость: текущая система уже монохромна — и токены серых (`design-tokens.ts:17`–`:29`), и палитра графиков `--chart-1…--chart-5` как серая шкала (`globals.css:136`–`:140`). Это идеальная отправная точка: цвет вводится осознанно и только для идентичности категорий.

**Светлая и тёмная темы.** Сейчас продукт светлый принудительно (`globals.css:24`), и причина документирована: прозрачные поверхности над WebGL-градиентом, спроектированным под белое. Для Eco рекомендация: **все цвета графиков и сумм берутся из CSS-переменных с первого дня, ни одного литерала в компонентах.** Тогда тёмная тема — это подмена токенов плюс отдельная работа с шейдером и прозрачностями, а не переписывание визуализаций. Порядок: светлая тема в релиз, тёмная — отдельным решением с честной оценкой стоимости (второй набор палитр графиков, ревизия всех прозрачных поверхностей, второй набор цветов ColorBends).

### 5.9 Пустые состояния, первый запуск, aha-момент

**Целевое время до aha — 90 секунд, и до любой настройки.**

Сценарий:

1. **0–10 с.** Один вопрос: «Сколько сейчас на основной карте?» Одно поле, одна кнопка. (Внутри создаётся счёт и проводка с «Начальных остатков» — пользователь этого не видит.)
2. **10–60 с.** «Что ты потратил сегодня?» — строка естественного ввода, чипы-подсказки типичных трат. Пользователь вводит 2–4 операции по памяти. Каждая запись мгновенно меняет остаток на экране.
3. **60–90 с. Aha.** Продукт показывает то, что пользователь сам посчитать не мог. Варианты, в порядке силы: (а) «при таком темпе месяц закроется на 42 800 ₽»; (б) «эти 4 подписки стоят 21 500 ₽ в год»; (в) «денег хватит до 14 марта».

**Ключ: aha — это число, которого пользователь не знал, а не экскурсия по интерфейсу.** Тур, чеклист онбординга, «5 шагов до настройки» — всё это стоимость без ценности.

**Отвергнуто:** мастер настройки (счета → категории → бюджеты → цели). Причина — вся стоимость настройки взимается до первой пользы; это стандарт индустрии и одновременно её главный обрыв (блок 2, причина 5).

**Пустые состояния.** Правило: в пустом состоянии должен быть **работающий элемент управления и правдоподобный пример**, а не иллюстрация с надписью «Нет данных». Пустой список операций — это строка ввода с примером «кофе 350». Пустой бюджет — это «Обычно ты тратишь ~28 000 в месяц. Разложить по конвертам?» с кнопкой. Пустой Inbox — единственное пустое состояние, которое можно и нужно праздновать.

### 5.10 Мобильный опыт и одна рука

Проект уже даёт основу: запрет зума на полях (`globals.css:476`), safe-area (`:487`), снятие тап-подсветки (`:465`), брейкпоинты сеток 1400/900/480 (`frontend/src/app/tasks/page.tsx:63`–`:68`), мобильная навигация-пилюля (`navbar.tsx:438`).

Правила для Eco:

- **Захват — в нижней трети экрана.** Основное действие продукта обязано быть в зоне большого пальца. Верхние углы — для навигации и второстепенного.
- **Числовая клавиатура открывается сразу** при открытии захвата; фокус на поле суммы; `Enter` коммитит.
- **Размер целей 44×44 px** для всех денежных действий. WCAG 2.2 SC 2.5.8 (AA) требует минимум 24×24, SC 2.5.5 (AAA) — 44×44 ([W3C/WCAG-обзор](https://www.wcag.com/developers/2-5-8-target-size-minimum-level-aa/)). Для Eco берём 44: цена промаха здесь — неверная запись о деньгах, а не лишний клик.
- **У каждого жеста есть видимая альтернатива.** Свайп по операции — удобно, но операция обязана иметь и явное меню: жест, о котором не знают, — это функция, которой нет.
- **Горизонтальные графики скроллятся внутри себя**, документ не скроллится по горизонтали никогда (уже обеспечено `globals.css:29`–`:38`).
- **Sankey и широкие таблицы на телефоне** — отдельный экран с зумом и пан-жестом, а не сжатая до неузнаваемости версия.

### 5.11 Доступность

- **Контраст.** Все суммы — это контент, а не декор: минимум 4,5:1. Приглушённые копейки на 0,6–0,7 прозрачности обязаны проверяться отдельно — легко уйти ниже нормы.
- **Смысл не в одном цвете** (WCAG 1.4.1). Из [5.8](#58-цвет) это следует автоматически: направление кодируется текстом и позицией.
- **Скринридеры.** Каждая сумма получает `aria-label` с развёрнутой формой: «минус двенадцать тысяч триста сорок пять рублей». Сырое `−12 345 ₽` читается непредсказуемо. Меняющийся баланс — `aria-live="polite"`, но **не на каждое нажатие клавиши** при вводе: иначе скринридер будет проговаривать промежуточные суммы.
- **`<html lang>` обязан стать `ru`** (сейчас `en`, `frontend/src/app/layout.tsx:74`). Для денежного интерфейса это не формальность: без правильного языка числа и валюта озвучиваются чужой фонетикой.
- **Клавиатура.** `N` — новая операция, `Cmd/Ctrl+K` — палитра команд, `Esc` — отмена с подтверждением при непустом вводе, `Tab`-порядок в форме сверху вниз без ловушек, видимый фокус (в проекте уже кольцо `ring-4`, `button.tsx:8`).
- **Числа не должны быть картинками.** Ещё одна причина против canvas/WebGL для графиков: подписи на SVG остаются текстом — их читает скринридер и их можно выделить.
- **Таблица как альтернатива графику.** У каждого графика — переключатель «показать таблицей». Это одновременно доступность и функция для власть-пользователей.

### 5.12 Пять интерфейсных идей, которых нет ни у кого

Это сердце исследования. Для каждой идеи: что это, почему работает, чего нет у других.

#### Идея 1. «Кривая правды» — календарь остатка вместо графика расходов

**Что.** Главный график продукта: одна линия — фактический остаток по всем ликвидным счетам в прошлом, и веер p25–p75 в будущем. На веер нанесены известные обязательные платежи как «зубцы» вниз с подписями. По горизонтали — дни, а не категории.

**Почему работает.** Деньги переживаются не как сумма, а как **момент нехватки**. Вопрос, который человек реально себе задаёт, — «когда станет тяжело», а не «сколько ушло на такси». Кривая отвечает именно на него. И второе: это **единственный график, на котором можно действовать**. Зубец можно схватить и перенести (перенести платёж), можно выключить (отменить подписку) — и веер перестраивается за ≤ 200 мс. График превращается из отчёта в инструмент.

**Чего нет у других.** Банки показывают прошлое (Monzo Trends, Revolut Analytics). YNAB показывает конверты. Copilot показывает категории. Прогнозная кривая остатка с интерактивными обязательствами — пустое место `[вывод по обзорам продуктов, не исчерпывающая проверка]`.

#### Идея 2. Переключатель единиц жизни

**Что.** В углу любого экрана — переключатель единиц: `₽` / `часы работы` / `дни свободы` / `% месячного потока`. Нажатие меняет **все** числа на странице. 65 000 ₽ становятся «118 часов работы» или «9 дней свободы».

**Почему работает.** Решение о покупке принимается в других единицах, чем ведётся учёт. И главное: **смена единиц измерения — это любопытство, а тот же факт репликой — это упрёк.** «Ты потратил 3 часа жизни на кофе» — осуждение (причина отказа №2). Переключатель °C↔°F — игра. Содержание одинаковое, судьба продукта разная.

**Чего нет у других.** Идея «реальной часовой ставки» известна из «Your Money or Your Life», но в продуктах она встречается как разовая плашка-поучение, а не как глобальная смена единиц измерения интерфейса `[вывод]`.

#### Идея 3. «Разнос за 20 секунд» — Inbox на одну руку

**Что.** Неразнесённые операции копятся в Inbox. Разбор — стопка карточек: одна операция на весь экран, 3–4 предсказанные категории крупными кнопками в зоне большого пальца, свайп вправо — принять лучшую догадку, свайп влево — отложить. Сверху всегда видно «осталось 4».

**Почему работает.** Три механизма сразу. **Конечность**: видимый счётчик превращает бесконечную повинность в задачу с концом. **Одна рука**: разбор делается в лифте и в очереди, то есть в те 20 секунд, которые у человека реально есть. **Право на «не знаю»**: отложить — легальный ход, и это снимает перфекционизм (причина отказа №8). Это доведённая до предела механика review у Copilot Money — с явным счётчиком остатка и одноручным управлением.

**Чего нет у других.** Copilot делает разбор красиво, но как список на планшетном экране. Очереди с явной конечностью и одноручным управлением в этой категории я не нашёл `[вывод]`.

#### Идея 4. «Личная инфляция» — твоя корзина против официальной

**Что.** Из повторяющихся покупок (одни позиции, одни мерчанты) строится индекс цен конкретного пользователя и сравнивается с официальным ИПЦ. Показ: две линии плюс список «что подорожало для тебя сильнее всего».

**Почему работает.** Это знание **невозможно получить никаким другим способом**, и оно немедленно объясняет самое частое финансовое ощущение — «зарабатываю столько же, а хватает меньше». Оно не осуждает (виноваты цены, не пользователь) и при этом ведёт к действию (заменить подорожавшее, перезаключить договор).

**Цена.** Требует детализации до позиций — то есть чеков и OCR. Это фича второй версии, но **схема обязана допускать позиции внутри операции с самого начала**, иначе потом потребуется миграция всего леджера.

#### Идея 5. «Два числа и предложение» вместо дашборда

**Что.** Главный экран — ровно два числа (безопасно сегодня; чистая стоимость и дельта) плюс **одно конкретное предложение**, выведенное из данных: «Подписка «X» — 5 988 ₽/год, последние 3 месяца не использовалась. Отменить?» Всё остальное — на втором уровне.

**Почему работает.** Whoop и Oura доказали: одно число с объяснением удерживает лучше двадцати графиков ([WHOOP](https://www.whoop.com/us/en/thelocker/how-does-whoop-strain-work-101/), [Oura](https://ouraring.com/blog/readiness-score/)). А финансовые продукты проигрывают не от недостатка данных, а от того, что не выдают **решение** (причина отказа №4). Предложение — это готовое решение, а не наблюдение.

**Ограничение, без которого идея вредна:** предложение обязано быть **выводимым и объяснимым** (вот подписка, вот 3 месяца без транзакций от неё), а не результатом непрозрачного скоринга. И оно обязано иметь кнопку «не предлагать такое» — иначе это спам.

#### Бонус. Сверка как ритуал, а не как аудит

Раз в неделю — один вопрос: «Сколько реально на карте?» Одно поле, одна кнопка, 20 секунд. Разница либо объясняется списком кандидатов, либо становится честной корректировкой. **Почему это идея, а не функция:** расхождение цифр с реальностью — причина тихого отказа №8, и это единственная механика, которая его лечит. Продукты либо не имеют сверки вовсе (трекеры), либо имеют её в бухгалтерском виде на десятки строк (GnuCash, Firefly III). Сверка на один вопрос — пустая ниша.

### 6.1 Схема данных с обоснованием

| `scenarios` | имя, дельты (JSONB) | — |
| `outbox`, `inbox` | по образцу проекта | `INV-COMM-3/4/5` |

**Три осознанные денормализации, каждая с причиной:**

1. **`postings.base_amount_minor` + `fx_rate`** — заморозка курса на дату операции. Без неё исторические отчёты «плывут» (см. [3.2](#32-мультивалютность)).
2. **`postings.booked_on`, дублирующая заголовок транзакции.** Это главная денормализация схемы: без неё **любой** запрос по диапазону дат обязан соединяться с `transactions`, а таких запросов в продукте — почти все. Цена — поддержание согласованности внутри агрегата (дата меняется только через корень, что и так требует `INV-DATA-1`).
3. **Снапшоты периодов** — иммутабельность закрытых периодов (см. [3.9](#39-периоды-закрытие-снапшоты)).

Всё остальное нормализовано строго: леджер — источник правды, и дублирование в нём стоит дороже, чем join.

### 6.2 Индексы

| Таблица | Индекс | Зачем |
|---|---|---|
| `postings` | `(user_id, booked_on DESC, id)` | основной индекс продукта: лента, месяц, период |
| `postings` | `(account_id, booked_on DESC)` | остаток и история счёта, сверка |

| `transactions` | UNIQUE `(user_id, client_id)` | идемпотентность записи из офлайн-очереди |

**Отвергнуто:** BRIN по `booked_on`. Причина — BRIN выигрывает на десятках миллионов строк с высокой физической коррелированностью; на 10^5 строк на пользователя btree быстрее и предсказуемее.

**Отвергнуто:** индекс по нормализованному мерчанту через `pg_trgm` в v1. Причина — поиск по мерчанту на 10^5 строк работает и без него; добавлять при реальной необходимости.

### 6.3 Объёмы и партиционирование

Расчёт из [3.9](#39-периоды-закрытие-снапшоты): активный пользователь за 10 лет — ≈ 36 500 транзакций, ≈ 91 000 проводок, ≈ 20–25 МБ с индексами `[расчёт мой]`. Снапшоты: 120 месяцев × ~40 категорий ≈ 4 800 строк — пренебрежимо.

| Масштаб | Проводок | Решение |
|---|---|---|
| 1 пользователь, 10 лет | ~10^5 | ничего не нужно: агрегация на чтении + снапшоты для иммутабельности |
| 100 пользователей, 10 лет | ~10^7 | тот же дизайн; следить за планами запросов |
| 1 000+ | ~10^8–10^9 | **тогда** RANGE-партиционирование по `booked_on` погодично |

**Отвергнуто:** партиционирование с первого дня. Причина — растёт время планирования, индексы дробятся, операционная сложность реальна, а выгода при 10^5 строк на пользователя нулевая. Партиционирование — ответ на измеренную проблему, а не профилактика.

### 6.4 Redis: что кэшировать и как инвалидировать

Опора на существующую конвенцию: ключи строятся `CacheKeyBuilder`, префикс = имя сущности для низкой кардинальности метрик, TTL задаётся на месте вызова (`docs/caching.md:25`, `:104`–`:106`).

| Кэшируем | TTL | Инвалидация | Почему можно |
|---|---|---|---|
| Агрегат дашборда `(user, period)` | 60 с | любая запись проводки пользователя | пересчёт дешёвый, но при `force-dynamic` экономит TTFB на повторных заходах |
| Курс валюты на дату | часы | нет (исторический курс неизменен) | чистая справочная величина |
| Таблица правил и MCC-маппинг пользователя | часы | изменение правил | читается на каждом вводе |
| Предсказание категории по мерчанту | часы | правка категоризации пользователем | горячий путь ввода, целевые 3 секунды |
| Лимит частоты импорта | — | — | защита от загрузки одного файла десять раз |

**Не кэшируем никогда:**

- **Остатки счетов.** Остаток должен быть точным; устаревший на 60 секунд остаток — это неверное «безопасно потратить» и подорванное доверие. Вычислять из снапшота на конец месяца + дельта проводок после него.
- **Данные сверки.** Сверка — это ритуал установления правды; кэш здесь противоречит смыслу операции.
- **Любые суммы для отображения на экране записи.** Подтверждение операции показывает актуальное число.

### 6.5 Приватность

**Что нельзя логировать никогда.** Расширение `INV-OBS-2` и `LogSanitizer` для домена Eco:

- суммы и остатки — **в любой форме**, включая «сумма превысила лимит на N»;
- имена плательщиков/мерчантов и нормализованные строки;
- номера и маски счетов, названия банков в связке с пользователем;
- заметки к операциям и имена файлов чеков;
- содержимое импортируемых файлов, включая при ошибке разбора (соблазн залогировать «плохую строку» — прямая утечка);
- любая комбинация `userId` + сумма, даже в отладочном сообщении.

Бизнес-события (`IBusinessEventLogger`, `INV-OBS-3`) для Eco несут **только количества и идентификаторы**: «импорт: 214 строк, 2 новых», но не суммы. И отдельно: `OpenTelemetry:Tracing:CaptureDbStatementText` для Eco должен остаться выключенным навсегда — параметры SQL здесь и есть суммы (`INV-OBS-5`).

**Шифрование: где уместно и где это театр.**

| Данные | Решение | Почему |
|---|---|---|
| Заметки, сырые строки мерчантов, файлы чеков | шифрование на уровне приложения через ASP.NET Data Protection (ключи в Redis — механизм уже используется для TOTP, `INV-AUTH-5`) | свободный текст не агрегируется и не индексируется — шифровать дёшево |
| **Суммы** | **не шифровать** | шифрованную сумму нельзя просуммировать, сравнить и проиндексировать; продукт превращается в клиентский калькулятор. Угроза «дамп базы» правильно закрывается шифрованием диска и бэкапов плюс контролем доступа, а не шифрованием колонки |
| Маски номеров счетов | хранить только последние 4 цифры, без полного номера | минимизация: полный номер продукту не нужен ни для чего |

**Экспорт и удаление.** Полный экспорт: JSON (все сущности), CSV (операции) и **текстовый двойной леджер, совместимый с Beancount** — последнее почти бесплатно, потому что модель уже двойная, и это сильнейший сигнал доверия (см. блок 2, причина 10). Удаление: Eco подписывается на `UserDeletedIntegrationEvent` (событие уже существует, `BuildingBlocks/.../Events/UserDeletedIntegrationEvent.cs`; Todo и Category его уже потребляют, `docs/architecture.md:184`–`:185`) и **физически удаляет** леджер, а не помечает флагом. В проекте есть прецедент политик хранения (`Services/TodoApi/Planora.Todo.Infrastructure/Retention/`).

**152-ФЗ.** Ключевые требования, релевантные Eco: первичный сбор, запись, систематизация, накопление и хранение персональных данных граждан РФ должны производиться в базах, физически расположенных на территории РФ; оператор обязан зарегистрироваться в Роскомнадзоре и получать согласие субъекта ([разбор требований](https://wcr-consulting.com/blog/2026/03/13/lokalizaciya-baz-dannyh-personalnyh-dannyh/), [обзор 2026](https://www.klerk.ru/blogs/roskom24/674017/)).

Практические следствия и открытая проблема:

- транзакционные данные формально не относятся к специальным категориям ПД, но по факту это самая чувствительная информация о человеке после медицинской `[вывод]`;
- **в репозитории есть конфигурации развёртывания на Fly.io** (`deploy/fly/`), а его регионы находятся вне РФ — это прямой конфликт с локализацией, если продукт обслуживает граждан РФ. Вынесено в [Открытые вопросы](#открытые-вопросы);
- сторонняя аналитика и CDN для этого домена — отдельный риск по тому же основанию;
- **дисклеймер:** это не юридическое заключение. Перед публичным запуском нужна консультация юриста; настоящий раздел лишь фиксирует, что вопрос архитектурный, а не «оформительский».

### 6.6 События RabbitMQ

Всё через outbox (`INV-COMM-3`), потребители идемпотентны (`INV-COMM-4`).

**Eco публикует** (имена индикативные):

| Событие | Потребитель | Полезная нагрузка |

| `EcoBudgetThresholdCrossed` | Realtime → уведомление | id конверта, факт пересечения. **Без суммы и без слова «перерасход»** |

### 6.7 Офлайн и оптимистичные обновления

**Должен ли ввод работать без сети.** Да — но в ограниченном смысле. Развилка:

| Вариант | Сложность | Что даёт | Вердикт |
|---|---|---|---|
| Ничего: без сети ввод недоступен | 0 | — | нет: метро, самолёт, дача — ровно те места, где записывают траты |
| **Офлайн-захват: очередь записей в IndexedDB + локально пересчитываемый остаток** | средняя | ввод всегда работает, целевые 3 секунды не зависят от сети | **да** |
| Полный local-first с CRDT (как Actual Budget) | высокая | офлайн-всё, включая отчёты и правки | нет в v1 |

**Что это значит для схемы — три требования, и все они дешевле сейчас, чем потом:**

1. **Id генерируется клиентом.** Проект уже к этому готов: `Guid` присваивается в конструкторе сущности (`BaseEntity.cs:18`). Рекомендация — **UUIDv7** вместо v4 для транзакций и проводок: он time-ordered, то есть вставка идёт в конец btree, а не случайно по всему индексу.
2. **Каждый эндпоинт записи идемпотентен по клиентскому id** (UNIQUE `(user_id, client_id)`). Это одно решение закрывает три проблемы: повторную отправку из очереди, двойное нажатие и дубли при плохой сети.
3. **Разрешение конфликтов — last-writer-wins по полю + `xmin`.** CRDT не нужен: домен однопользовательский, и одновременная правка **одной и той же** транзакции с двух устройств — редчайшее событие. Оптимистичная блокировка через `xmin` (`TodoDbContext.cs:24`) уже даёт корректное поведение «кто-то изменил, перезагрузи».

**Честная цена офлайн-захвата:** клиент обязан уметь считать остаток локально, иначе оптимистичная запись покажет устаревший баланс — а это ровно то, что запрещено в [6.4](#64-redis-что-кэшировать-и-как-инвалидировать). Значит на клиенте нужен минимальный локальный дериватор: остаток на начало дня плюс локальные записи.

**Отвергнуто:** CRDT как у Actual Budget. Причина — Actual решает задачу мультидевайсной синхронизации файла-бюджета без сервера истины; у нас есть сервер истины и один владелец данных. CRDT здесь — многократное усложнение ради сценария, который почти не наступает.

**Отвергнуто:** `bigint identity` вместо `Guid`. Причина — противоречит `BaseEntity` всего проекта и делает невозможной клиентскую генерацию id, то есть убивает офлайн-захват и идемпотентность.

## Блок 7 — Сцепка с Planora

Тезис: **финансовый сервис внутри Planora может уметь то, чего не умеет ни один отдельный финансовый продукт — потому что у него есть доступ к задачам, целям, календарю, дружбам и живым уведомлениям одного и того же человека.** Ни Monarch, ни YNAB, ни Copilot не знают, что пользователь собирается менять машину, — а Planora знает, потому что это задача.

Для каждой сцепки: ценность и цена в сложности.

### 7.1 Задача со стоимостью

**Что.** У задачи появляется планируемая и фактическая стоимость. Eco показывает «запланировано задачами на этот месяц: 84 000 ₽» и включает это в прогноз. Когда трата записана, она привязывается к задаче, и задача показывает «вышло 91 200 вместо 84 000».

**Ценность: высокая.** Это единственное место во всём ландшафте, где «починить машину» и «40 000 ₽» — один и тот же объект. У прогноза появляется то, чего нет ни у кого: **знание о намерениях, а не только об истории.** Прогноз из повторяющихся платежей плюс медианы — статистика; прогноз, знающий про запланированный ремонт, — уже планирование.

**Цена: средняя.** Eco хранит непрозрачный `todo_id` без FK (`INV-OWN-1`), отображение подтягивает батчевым gRPC — паттерн уже применяется (`GetUserProfilesBatch`, `docs/architecture.md:175`). Надо стерпеть висячие ссылки: задачу могут удалить, и Eco обязан не падать, а обнулить привязку (прецедент — `CategoryDeletedEventHandler` в Todo). Обратная сторона — поле стоимости в агрегате `TodoItem`, то есть изменение чужого домена; это отдельное решение и отдельный ADR.

### 7.2 Цель как проект

**Что.** Финансовая цель («накопить 600 000 на первый взнос») — это и сумма с прогрессом, и дерево задач в Todo («собрать документы», «сравнить ставки»).

**Ценность: высокая.** Цели в финансовых приложениях умирают, потому что цель — это только число, а число само не движется. Присоединённые шаги превращают цель в проект. Плюс у Planora уже есть подзадачи с деревом и совместная работа (`docs/features.md` → Subtasks).

**Цена: средне-высокая.** Два агрегата в двух сервисах и один UI поверх них; нужны согласованные состояния («цель достигнута» ↔ «задачи закрыты») и решение, кто главный. Рекомендация — **Eco владеет целью, Todo владеет шагами**, связь односторонняя: цель знает про корневую задачу, задача про цель не знает.

### 7.3 Повторяющиеся платежи в одном календаре с задачами

**Что.** Платёж по кредиту 12-го и «позвонить в страховую» 12-го — в одном календаре, одним списком.

**Ценность: высокая при низкой добавочной стоимости.** Это то, ради чего люди держат финансовое приложение открытым: не аналитика, а «не забыть заплатить». И это именно то, что монопродукт сделать не может — у него нет остальных дел пользователя.

**Цена: низкая-средняя.** Eco публикует наступающие платежи, календарный вид их отображает как проекцию только для чтения. **Важно: Eco не пишет в Todo** — платёж не превращается в задачу автоматически, иначе домены переплетаются и владение размывается. Кнопка «сделать задачей» — пользовательское действие, а не автоматика.

### 7.4 Совместные траты поверх существующих friendships

**Что.** Общее пространство («поездка в Казань», «квартира») с участниками из уже принятых дружб; траты, доли, расчёт «кто кому сколько».

**Ценность: очень высокая.** Splitwise — отдельное приложение, из которого люди не уходят только потому, что альтернативы нет. Planora уже владеет дружбами (Auth, `INV-OWN-2`), уже имеет gRPC-проверку дружбы и уже имеет прецедент шаринга с редакцией контента.

**Цена: высокая.** Три отдельные сложности: (1) арифметика взаиморасчётов и минимизация числа переводов; (2) **приватность** — участник видит общую трату и не видит остальной леджер, что требует редакции на уровне DTO по образцу `HiddenTodoDtoFactory` и `INV-AZ-3`; (3) согласие и отзыв доступа при удалении дружбы (потребление `FriendshipRemovedIntegrationEvent`, прецедент в Todo есть). Плюс новая поверхность IDOR, а значит обязательная запись в `docs/security-idor-coverage.md` по `INV-AZ-8`.

Рекомендация по модели: **общие траты — отдельное пространство с собственными счетами-контрагентами, а не флаг на операции личного леджера.** Иначе редактирование доли одним участником меняет чужой баланс, и права становятся неразрешимыми.

### 7.5 Уведомления через существующий Realtime

**Что.** «Завтра платёж по кредиту», «в общем пространстве новая трата», «Inbox: 6 неразнесённых».

**Ценность: высокая, стоимость почти нулевая.** Инфраструктура готова целиком: `NotificationEvent` через outbox, Realtime персистит в свой read-model и рассылает по SignalR, непрочитанные считаются, офлайн-получатель догоняется при переподключении (`docs/architecture.md:234`–`:240`).

**Цена: низкая.** Единственное ограничение — совпадающее с нашим же правилом приватности: полезная нагрузка остаётся тонким сигналом, клиент дозапрашивает содержимое через авторизованный эндпоинт. Суммы не летят через шину.

Тон уведомлений — из [5.6](#56-тон-и-эмоция): «завтра списание 24 000 ₽ по кредиту» — да; «вы слишком много потратили» — никогда.

### 7.6 Общий логин и единый визуальный язык

Ничего строить не нужно: JWT выпускает Auth, доступ проверяет шлюз, gRPC защищён сервисным ключом. Маршрут — `/eco/api/v1/{everything}` по образцу `ocelot.json:159`, на свободном порту (занято 5030/5032/5058/5060/5100/5281). Визуальный язык — существующие токены и анимации, без форка дизайн-системы.

### 7.7 Чего связывать НЕ надо

| Соблазн | Почему нет |
|---|---|
| Единая таксономия категорий через CategoryApi | разная семантика, навязанные изменения между доменами, размытая граница (подробно в [3.6](#36-категоризация)) |
| Реплика таблиц Todo внутри Eco «для скорости отчётов» | прямое нарушение `INV-OWN-1`; реплика разойдётся, и это будет невидимо |
| Автоматическое превращение каждого платежа в задачу | шум в Todo, размытое владение, необратимость |
| Комментарии к операциям через Collaboration | Collaboration построен вокруг задач и их прав доступа; денежные обсуждения — другая модель доступа. Заметка к операции — поле, а не тред |
| Сообщения об операциях через Messaging | суммы в мессенджере — утечка по определению |

## Блок 8 — Нейминг

### 8.1 Проблема рабочего имени «Eco»

- **В английском** `eco` — устойчиво «экологический»: eco-friendly, eco-mode, ecosystem. «Planora Eco» прочитывается как зелёная инициатива или энергосберегающий режим.
- **В русском** «эко» — это экология и ЭКО (репродуктивная медицина). «Экономика» из «эко» не достаётся: русский сокращает экономику до «эконом», и это слово означает дешёвый класс — то есть ровно противоположное заявленному «не про экономию».
- **SEO и различимость** — нулевые: «eco app» не гуглится ни на одном языке.
- **Точность** — обратная. Продукт про то, что деньги стоит понимать, а имя говорит про режим сбережения.

Вердикт: **имя противоречит позиционированию и в обоих языках, его надо менять.**

### 8.2 Альтернативы

Критерии оценки: смысловая точность (×5), читаемость по-русски вслух (×4), различимость и незанятость в категории (×3), пригодность для namespace/URL/имени БД (×3), тональность — уважение без пафоса (×3). Шкала 1–5.

| Имя | Точность (×5) | Русская речь (×4) | Различимость (×3) | Технич. пригодность (×3) | Тональность (×3) | Итого |
|---|---|---|---|---|---|---|
| **Ledger** | 5 | 2 | 4 | 5 | 4 | **72** |
| **Flow** | 4 | 4 | 2 | 5 | 4 | **69** |
| Capital | 4 | 4 | 3 | 5 | 2 | **66** |
| Worth | 5 | 1 | 5 | 4 | 4 | **68** |
| Tally | 3 | 1 | 5 | 5 | 5 | **64** |
| Means | 3 | 1 | 4 | 4 | 4 | **55** |
| Pulse | 2 | 4 | 1 | 5 | 3 | **53** |
| *Eco (текущее)* | 1 | 3 | 1 | 5 | 2 | **41** |

Разбор кандидатов:

- **Ledger** — «книга учёта». Точно описывает суть: двойная запись, единственный источник правды. Для разработчика имя само сообщает главный инвариант. `Planora.Ledger.*`, `planora_ledger`, `/ledger`. Минус — по-русски не произносится («леджер» звучит как жаргон) и непонятно неспециалисту.
- **Flow** — денежный поток, главная метафора продукта («Кривая правды», прогноз, Sankey). Короткое, произносимое, ложится всюду. Минус — слово занято в индустрии до предела (язык Flow, десятки продуктов), различимость низкая.
- **Capital** — точно бьёт в «экономика, а не экономия», поднимает статус. Минус — инвестиционно-богатая тональность, которая отталкивает того, у кого капитала нет, то есть большинство. Для продукта про уважение это плохой первый сигнал.
- **Worth** — «стоимость / чего это стоит» + net worth. Смысл идеальный, различимость высокая. Минус — по-русски мертво: «ворт» не читается, склонять нечем.
- **Tally** — «подсчёт, зарубка на палке». Тёплое, человеческое, редкое, отличная техническая пригодность. Минус тот же: русскому уху пусто.
- **Means** — «средства» и «значит» одновременно. Красиво и слишком тонко: в каталоге и в поиске не работает.
- **Pulse** — занято абсолютно всем, от здоровья до аналитики.

### 8.3 Рекомендация

**Расщепить две работы, которые обычно пытаются свалить на одно слово.**

- **Техническое имя — `Ledger`.** Namespace `Planora.Ledger.Api/Application/Domain/Infrastructure`, база `planora_ledger`, схема `ledger`, маршрут шлюза `/ledger/api/v1/{everything}`, gRPC-контракт `ledger.proto`. Обоснование: технические имена должны быть точными и стабильными на годы; `Ledger` сообщает каждому будущему разработчику главный инвариант домена («сумма проводок равна нулю») без единой строчки документации.
- **Пользовательское имя раздела — «Деньги».** Четвёртая вкладка в навигации (`navbar.tsx:22`–`:25`) рядом с Dashboard / Tasks / Categories. Обоснование: пользовательское имя обязано быть неоспоримым по-русски и не требовать объяснений. «Деньги» невозможно прочитать неправильно, оно короткое (6 символов — влезает в мобильную пилюлю), и оно не обещает ни экономии, ни богатства.

**Если одно слово обязано делать обе работы** — брать **Flow** (`Planora.Flow.*`, `planora_flow`, `/flow`, раздел «Поток»): второй результат в таблице и единственный кандидат, приемлемый одновременно в namespace и в русской речи.

**Отвергнуто:** сохранить `Eco` как техническое имя, а наружу показывать «Деньги». Причина — техническое имя живёт в коде десять лет и формирует мышление тех, кто его читает; имя, означающее «экология», будет вечно требовать сноски, а его буквальное прочтение («эконом-режим») прямо противоречит замыслу продукта.

`[требует проверки]` Доступность доменов и торговых марок для любого из имён я проверить не могу — это отдельная задача. Отмечу лишь, что для раздела внутри Planora отдельный домен, скорее всего, не нужен вообще.

## Открытые вопросы

Всё, что требует решения пользователя, с вариантами и последствиями выбора.

**1. Аудитория: инструмент для себя или продукт для рынка?**
(а) Только для себя — можно выкинуть онбординг, мультипользовательские сценарии и половину соображений про порог входа, и сразу брать «строгий» режим. (б) Продукт — тогда блок 2 определяет приоритеты сильнее, чем блок 3. Это первый вопрос, потому что он меняет вес всех остальных.

**2. Хостинг и 152-ФЗ.** В репозитории лежат конфигурации Fly.io (`deploy/fly/`), регионы которого вне РФ, а локализация ПД граждан РФ требует хранения на территории РФ. Варианты: (а) отечественный хостинг для Eco (и, вероятно, для всего Planora); (б) Eco только как self-hosted/локальный инструмент без обработки чужих ПД; (в) юридическая проработка. Вопрос архитектурный: он определяет, где живёт база.

**3. Мультивалютность в первой версии: да или нет?** Рекомендация — **да, на уровне схемы и хранения курсов, даже если в UI сначала одна валюта**. Причина — исторические курсы нельзя добыть задним числом. Но объём работы это заметно увеличивает, и решение за вами.

**4. Строгий zero-based (YNAB-режим): опция, отсутствует или основа?** Рекомендация — опция. Если вы лично пользуетесь методом YNAB, ответ может быть другим, и тогда он становится основой.

**5. Импорт выписок в v1: какие банки?** Каждый банк — свой парсер плюс профиль. Вопрос: начинаем с одного (какого?), с универсального сопоставителя колонок, или отказываемся от импорта в первой версии в пользу идеального ручного ввода?

**6. Тёмная тема.** Сейчас продукт светлый принудительно и по документированной причине (`globals.css:15`–`:25`). Варианты: (а) остаёмся светлыми, Eco проектируется под белое; (б) тёмная тема как отдельный проект для всего Planora. Промежуточного варианта «тёмная тема только в Eco» нет — это сломает единство.

**7. Инвестиции: в v1, позже или никогда?** Решение не про фичу, а про схему: проводка должна уметь нести количество и единицу, иначе добавление позже потребует миграции всего леджера. Рекомендация — заложить в схему, не реализовывать в UI.

**8. Совместные траты: v1 или v2?** Ценность наивысшая, сложность наивысшая, новая поверхность IDOR. Рекомендация — v2, но модель пространств заложить в схему.

**9. Чеки и позиции.** Нужны для «личной инфляции» (идея 4) и для честного TCO. Рекомендация — таблица позиций в схеме с самого начала, OCR позже.

**10. Название.** `Ledger` + раздел «Деньги», либо `Flow` как единое имя, либо ваш вариант. Требует решения до создания первой папки, потому что namespace потом не переименовывают.

**11. Библиотека визуализации.** Рекомендация — свой SVG. Если время дороже контроля — visx как второй выбор. Решение влияет на бандл и на CSP.

**12. Офлайн.** Рекомендация — офлайн-захват (очередь) в v1, полный local-first никогда. Если вы хотите полноценный офлайн, это меняет архитектуру фронтенда целиком, и решать надо сейчас.

**13. `INV-DATA-4` против леджера.** Soft-delete через глобальные фильтры — общий паттерн проекта, но для проводок он опасен (баланс, зависящий от того, кто спрашивает). Рекомендация — отклонение, оформленное ADR: удаление операции = сторно. Требует вашего согласия, потому что это осознанное отступление от инварианта.

## Что я НЕ рекомендую делать и почему

Соблазнительные идеи, которые убьют продукт. Каждая привлекательна, и именно поэтому опасна.

**1. ИИ-советник как главная фича** («спроси у ИИ про свои деньги»). Недетерминированный ответ про деньги разрушает доверие быстрее всего остального: одна галлюцинация в сумме — и пользователь больше не верит ни одному числу. Вся арифметика личных финансов детерминирована и объяснима, и это её главное достоинство. LLM полезна в трёх узких местах — нормализация мерчантов, подсказка категории, разбор чека — то есть как *предложение*, которое пользователь подтверждает.

**2. Геймификация с очками, уровнями и лидербордами.** Деньги — не игра, а сравнение доходов с другими людьми токсично в любом исполнении. Единственное допустимое сравнение — с собой прошлым (Strava-механика), и без счёта очков.

**3. Стрик за ежедневный ввод.** Работает у Duolingo и будет работать здесь — ровно до первого пропуска, после которого превратится в наказание и в стыд. Механика прощения (streak freeze) нужна именно потому, что стрик вреден; проще не вводить стрик. Вместо него — конечный Inbox, где успех это «очередь пуста», а не «не пропустил ни дня».

**4. Скор финансового здоровья 0–100.** Соблазн от Whoop, но у Whoop формула выводится из измерений самого пользователя. Финансовый скор неизбежно опирается на внешние нормативы («надо копить 20%»), то есть оценивает человека по чужой линейке. Одно число — да, но только выводимое из его собственных данных: «безопасно потратить сегодня», «runway до даты».

**5. Автокатегоризация без объяснения и без права на «нет».** Молчаливая неверная догадка хуже отсутствия догадки: она портит статистику, которую пользователь не проверял, и обнаруживается через месяц, обнуляя доверие ко всем отчётам.

**6. Полная неизменяемость записей с первого дня.** Аудит идеален, жизнь невозможна: за опечатку в сумме пользователь платит сторно-операцией. Барьер должен появляться на закрытии периода, а не на каждой правке.

**7. Двойная запись, вылезшая в UI.** Дебет, кредит, «сальдо», выбор двух счетов на каждую покупку. Это гарантированная смерть на онбординге — единственная причина, по которой GnuCash и Beancount остались инструментами для инженеров.

**8. Тридцать-сорок категорий по умолчанию.** Стандарт индустрии и активный вред: мёртвые категории разбавляют список выбора при вводе, замедляя главное действие продукта, и обесценивают бюджет.

**9. Парсинг PDF-выписок в первой версии.** Выглядит как «всего один парсер», на практике — бездонная яма: у каждого банка своя вёрстка, таблицы ломаются переносами страниц, сканы требуют OCR, а ошибка в сумме неотличима от правды. CSV/XLSX закрывают ту же потребность на порядок дешевле.

**10. Красный цвет для перерасхода.** Разобрано в [5.8](#58-цвет): морализация, недоступность для ~8% мужчин, перегруженность значения и потеря цветового канала для настоящей работы.

**11. Ставка на агрегацию через зарубежные API (Plaid и аналоги).** В РФ неприменимо, а Maybe Finance умер в том числе от того, что «интеграции обещали много и не дали» ([Failory](https://newsletter.failory.com/p/3-reasons-maybe-failed)). Ограничение рынка здесь — защита: продукт вынужден стать лучшим в вводе, а это и есть дифференциация.

**12. Пересчёт исторических отчётов по текущему курсу.** Отчёт, который меняется при повторном открытии, убивает доверие необратимо.

**13. Шифрование сумм на уровне полей.** Security theater: агрегация становится невозможна, продукт превращается в клиентский калькулятор, а реальная угроза (дамп базы) закрывается шифрованием диска и бэкапов.

**14. Микросервис на каждую подобласть** (`budgets-service`, `ledger-service`, `reports-service`). Бюджеты, проводки и отчёты связаны транзакционно: «записать операцию и обновить конверт» в разных базах — это распределённая транзакция там, где её не должно быть. Один сервис, одна база.

**15. Реплика данных Todo внутри Eco «для скорости отчётов».** Нарушает `INV-OWN-1`, и расхождение реплики будет невидимым.

**16. Уведомления вида «ты слишком много потратил».** Самый быстрый способ получить отключённые уведомления и удалённое приложение.

**17. Социальная лента вокруг денег.** Любая публичность трат либо порождает хвастовство, либо стыд. Совместные пространства — да; лента — никогда.

**18. Котировки, крипта и инвестиционная аналитика в v1.** Отдельный домен с внешними источниками, регуляторными рисками и бесконечной поддержкой. В схеме — место для позиций; в UI — позже.

**19. Импорт без дедупликации, «починим потом».** Один двойной импорт — и пользователь видит удвоенные расходы, то есть продукт врёт. Восстановление доверия дороже, чем хеш строки с самого начала.

**20. Отказ от снапшотов «потому что данных мало».** Данных действительно мало (расчёт в [3.9](#39-периоды-закрытие-снапшоты)), но снапшоты нужны для неизменности закрытых периодов, а не для скорости.

**21. Круговая диаграмма расходов как главный экран.** Каноническая картинка категории, и она отвечает на вопрос, который никто не задаёт. Человек спрашивает «сколько можно потратить» и «когда станет тяжело», а не «какая доля у категории "Прочее"».
