Этот комплект подготовлен для `4Keyy/Planora`, ветки `main`, commit `dc6b1781a24d43d967c418de30acda10fcafb8f9` 2026-11-02. Он является планом, а не разрешением на production, push, merge, миграцию, изменение GitHub settings или удаление веток. В исходной сессии разрешено только создание аудиторских артефактов. Прочитай актуальные проектные инструкции, этот файл, свой PROMPT, `TASKS.json`, связанные findings и результаты предшественников. `TASKS.json` задаёт блокирующие зависимости; упоминание соседнего пакета в evidence означает связь, а не дополнительное ребро DAG. При противоречии останови спорный пункт и запиши решение. Не выполняй устаревший план механически.

## Процесс одной задачи

1. Зафиксируй состояние и принятый scope. Сопоставь baseline с текущим кодом.
2. Воспроизведи дефект: изолированный regression test, красный до исправления. Для verification-only задач сначала получи доказательство; не изобретай дефект ради изменения.
3. Внеси минимальную коррекцию с сохранением внешнего поведения. Не меняй визуальную систему, текст, motion timing, сортировку, privacy и API незаметно.
4. Прогони targeted → связанные integration/contract → более широкие gates. Пропущенный или не запущенный тест не является успешным.
5. Сохрани evidence: SHA, cwd, команды, exit codes, counts, длительность, условия, seed, версии и ограничения. Для производительности — одинаковая методика before/after; тестовое время не равно latency продукта.
6. Выполни self-review и независимый review при доступности. Документируй изменения в единственном тематическом источнике.
7. Коммить только собственный завершённый diff по актуальному полномочию и проектному протоколу. Не использовать `git add .`, force-add, reset/clean. Push и любые remote mutations только если разрешены для новой сессии.

## Владение и общие файлы

Одна рабочая копия допускает одного писателя конкретного файла. `owner_scope` в `TASKS.json` задаёт владельца. Для пересекающихся файлов действует последовательный handoff, даже если DAG разрешает параллельные вычисления. Контракты BuildingBlocks принадлежат T01, брокер T05, frontend stores/hooks T10, shared CI/Compose/Fly T14, зависимости и scanner policy T12, схема/миграции T08. T09 передаёт T14 требуемую Redis-конфигурацию; T07 передаёт T14 production route/listener matrix. После contract freeze T01 не меняется параллельно с потребителями.

Пакеты исправления добавляют собственные профильные тесты. T13 начинает общий тестовый проход после этих пакетов и не редактирует их тесты одновременно. Пакеты готовят перечень doc deltas в своих result-файлах; централизованно обновляет поддерживаемые руководства T15. Собственные evidence/result-файлы можно писать каждому пакету сразу. Это предотвращает конфликт в `docs/API.md`, `docs/testing.md` и `CHANGELOG.md`.

## Ограничения среды

- Windows PowerShell 5.1: проверяй `$LASTEXITCODE`; `;` не останавливает следующий шаг при ошибке. Нельзя считать общий exit последней команды успехом всей пачки.
- На машине аудита SDK 10.0.300 находится в `C:\Users\fkeyy\.dotnet\dotnet.exe`; системный `dotnet` на PATH был 8.0.133. Путь специфичен для машины, сначала проверить `--version`.
- Не запускай базовый Compose против имеющихся volumes. В нём фиксированные container names/ports, активны retention и startup schema changes. `COMPOSE_PROJECT_NAME` сам по себе не изолирует окружение.
- PostgreSQL suites могут создавать/удалять БД; `PLANORA_TEST_POSTGRES` должен указывать только на отдельно проверенный disposable сервер. Testcontainers может скачивать image: это отдельная подготовка окружения.
- Frontend build может переписать `next-env.d.ts`/tsconfig. Нужны проверенный собственный checkout либо согласованная изоляция, свободный порт и `NEXT_DIST_DIR`; не восстанавливай чужие изменения вслепую.
- Никаких нагрузочных проверок production. Миграции: expand → backfill → verify → contract, backup и проверенный restore; откат приложения не откатывает данные.

## Pass/fail и отчёт

Не понижать coverage ratchets, не удалять failing tests, не выключать security gate и не добавлять `continue-on-error` для обязательных проверок. CONFIRMED означает доказанное утверждение указанного масштаба: статическая коллизия очереди не означает выполненный broker experiment.

Результат пакета — `results/Txx.md`: baseline/final SHA, закрытые finding IDs, изменённые файлы, red/green evidence, команды/exit/counts, security/privacy matrix, UX screenshot matrix либо обоснованное N/A, показатели, migration/rollback review, doc deltas, ограничения и статус PASS / FAIL / BLOCKED. Для каждого acceptance item отдельный результат. Непройденный обязательный gate оставляет пакет незавершённым. Не делай чужой push/merge для получения зелёной галочки.
