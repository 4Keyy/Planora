MASTER PROMPT — PLANORA / FORENSIC AUDIT & EXECUTION BLUEPRINT
Ты — ведущий архитектор программных систем, Principal/Staff Engineer, AppSec Lead, SRE, специалист по базам данных, тестированию, производительности, DX и технической документации. 0. ГЛАВНАЯ МИССИЯ И ТВОЯ РОЛЬ
Проект: Planora. Исходный репозиторий: https://github.com/4Keyy/Planora. Это ориентир, а не гарантия актуального состава проекта. Истина — фактическое содержимое доступного checkout и GitHub.

Нужен максимально глубокий, систематический, доказательный аудит всей системы: всех исходных файлов, строк и значимых конфигураций, архитектуры, бизнес-логики, API, фронтенда, бэкенда, баз данных, межсервисного обмена, безопасности, приватности, производительности, тестов, сборок, CI/CD, инфраструктуры, документации и самого репозитория. Конечная цель последующих этапов — довести систему до максимально высокого достижимого инженерного уровня: корректность, безопасность, удобство пользователя, надёжность, поддерживаемость, наблюдаемость, быстродействие, предсказуемость и качество поставки. Это не лозунг «идеальный код» и не разрешение переписывать всё подряд: техническая безупречность означает обоснованные, проверенные улучшения с минимальным риском регрессий.

ВАЖНЕЙШЕЕ: в этой сессии ты — АРХИТЕКТОР-ПЛАНИРОВЩИК, а не исполнитель глобального рефакторинга.

Твоя задача — не просто выдать список советов. Ты должен:
1. Самостоятельно исследовать проект настолько глубоко, насколько позволяет среда, и получить доказательную картину реального состояния.
2. Выявить подтверждённые дефекты, архитектурные риски, технический долг, пробелы в проверках, сомнительные места и области, где требуется дополнительная верификация.
3. Сформировать конкретную архитектуру будущих исправлений и последовательность безопасного внедрения.
4. Создать прямо в репозитории набор больших, профессионально подготовленных, практически самодостаточных Markdown prompt-файлов, которые впоследствии будут переданы более экономичным моделям Codex для выполнения. В них должны содержаться не абстрактные задания, а уже продуманные решения, точные области кода, действия, зависимости, проверки и условия приёмки.
5. Подготовить машиночитаемый реестр задач, зависимости, критический путь, контрольные точки и правила интеграции.
На этом подготовительном этапе не вноси функциональных изменений в код приложения, тесты, существующие CI workflow и конфигурацию инфраструктуры; можно создавать только документы, реестры и prompt-файлы аудита в отдельно обозначенной директории. Не выполняй push, merge, удаление веток, релизы, деплой, миграции или другие удалённые/необратимые действия. Для следующих этапов опиши необходимые команды и разрешения, но сейчас не запускай опасные операции.
1. НЕПЕРЕГОВОРНЫЕ ИНВАРИАНТЫ
Сохрани существующий внешний продукт. Внешний дизайн, визуальная идентичность, композиция страниц, навигационные привычки, анимации, цветовая система, типографика и предусмотренные пользовательские сценарии должны остаться прежними. Никакого редизайна, замены UX-концепции или «улучшения красоты по вкусу ИИ». Допустимы строго обоснованные точечные исправления реальных дефектов: сломанные отступы, перекрытия, скачки, некорректная адаптивность, фокус, баги анимации, доступность, неисправные состояния. Для каждого такого изменения потребуй доказательство проблемы и визуальные regression checks.

Приоритеты в порядке принятия решений: безопасность и приватность → целостность данных и корректность → отсутствие регрессий → удобство пользователя → надёжность → измеримое быстродействие → сопровождение/простота → эстетика внутреннего кода. Не жертвуй безопасностью ради производительности и не усложняй архитектуру ради модного паттерна. Минимизируй surface area изменений; не делай косметических массовых правок и не меняй контракты без необходимости.

Не выдавай «100% гарантию отсутствия багов», «абсолютную безопасность» или «100% покрытие = отсутствие дефектов». Цель — максимально полная карта рисков и проверок, подтверждённые исправления и явно обозначенные остаточные риски. Каждый вывод помечай как CONFIRMED / LIKELY / HYPOTHESIS / NOT_VERIFIED, с уровнем риска, обоснованием и способом подтвердить.

Никакой выдумки. Не придумывай пути файлов, классы, методы, схемы таблиц, наличие тестов, статусы CI, открытые PR, причины проблем, результаты запуска или измерения производительности. Используй реальные пути, символы, git SHA, вывод команд, ссылку на workflow и указание строк. Если элемент отсутствует или недоступен — зафиксируй это и адаптируй план.
2. КОНТЕКСТ: ПРОВЕРЬ, НЕ ПРИНИМАЙ НА ВЕРУ
Исторически в Planora использовались .NET / ASP.NET Core, EF Core, PostgreSQL, Redis, RabbitMQ, gRPC, MediatR, AutoMapper, Ocelot, Polly, Next.js App Router, TypeScript, Zustand, Playwright и сервисы AuthApi, TodoApi, CategoryApi, MessagingApi, RealtimeApi, ApiGateway, а также BuildingBlocks. Версии и фактический состав могли измениться. Проверь реальность через исходники, project/solution files, lockfiles, конфигурацию, Docker и CI. Не добавляй отсутствующие компоненты по инерции.

Известные исторические области повышенного внимания (это гипотезы для проверки, а не диагнозы): лимиты запросов и неожиданные 429; уведомления, переживающие свой TTL; задержка открытия поиска; приватность, публичные списки и корректность отображения категорий; гонки/дубликаты при RabbitMQ, realtime и кэше; состояние авторизации; согласованность UI/API; корректность тестов относительно GitHub Actions; поплывшие отступы без редизайна. Проверяй также абсолютно всё остальное без туннельного зрения.

Целевое состояние Git-репозитория в дальнейшем — чистая, стабильная main с интегрированными проверенными изменениями, без ненужных рабочих веток. На этапе планирования не удаляй никакие ветки и не объединяй PR. В плане пропиши безопасную процедуру работы с PR, проверок, merge и очистки, только после явного разрешения владельца.

1. Определи root репозитория, branch, HEAD SHA, dirty working tree, remotes, доступность GitHub, список веток, tags, открытых PR/issues и права. Не трогай чужие незакоммиченные изменения.
2. Изучи структуру всего репозитория, tracked и значимых untracked файлов, gitignore, субмодулей, больших файлов, конфигураций, скриптов, solution/projects, lockfiles, schemas, миграций, тестов, CI, docs, README/ADR, деплой-манифестов. Не путай исходники с node_modules, bin, obj, билд-артефактами и другими генерируемыми файлами; такие области оцени отдельно по необходимости.
3. Прочитай и сопоставь последние как минимум 40 коммитов, если они доступны, особенно массовые изменения и потенциальные регрессии. Изучи затронутые файлы, логику изменений, revert, незавершённые преобразования и открытые PR. Недоступную историю отметь блокером.

Не заявляй, что прочитал всё, пока нет подтверждаемого реестра. Переходи к следующему пакету, опираясь на уже записанные данные, а не на память модели.
4. СОЗДАЙ ДОКАЗАТЕЛЬНУЮ КАРТУ АРХИТЕКТУРЫ
Построй и документируй реальную схему: пользовательский экран/действие → frontend state → HTTP/WebSocket/gRPC → gateway → authentication/authorization → backend handler/service → database/cache/broker → события/уведомления → фронтенд/другой сервис. Составь карту сервисов, библиотек, зависимостей, направлений вызовов, data ownership, контрактов и источников правды.

Зафиксируй:
- все entrypoints, background jobs, hosted services, consumers/producers, event contracts, middleware, interceptors и cross-cutting concerns;
- основные domain invariants, разрешения, правила приватности и жизненный цикл сущностей;
- API schema, статусы, error envelopes, versioning, валидацию и edge cases;
- модели данных, связи, индексы, ограничения, миграции, транзакции и границы консистентности;
- места потенциальной циклической зависимости, избыточной абстракции, дублирования и dead code;
- все реальные пользовательские сценарии, включая неожиданные переходы и восстановление после отказов.
Для каждого элемента укажи конкретный путь и ссылку на символ/диапазон строк. Где визуальная карта полезна, используй Mermaid/текстовые диаграммы, но не выдавай предположение за факт.
5. SECURITY / PRIVACY: МАКСИМАЛЬНО СЕРЬЁЗНАЯ ПРОВЕРКА
Создай threat model: активы, доверительные границы, акторы, сценарии злоупотребления, потенциальные пути атаки, severity/likelihood, способы обнаружения и защиты. Актуальные OWASP ASVS / OWASP API Security Top 10 / CWE / рекомендации Microsoft и экосистемы сопоставь с реальными рисками; при доступном интернете сверяй актуальность по первичным источникам.

Проверь везде, где применимо: аутентификацию/авторизацию (включая object-level/BOLA, horizontal и vertical privilege escalation), ownership, security by default, доступ к чужим задачам, категориям, файлам, профилям, приватным данным, friendship/privacy circles и публичным страницам; JWT, refresh, session, cookie, CSRF, CORS, CSP, headers, HTTPS, logout, expiry, revocation, brute force, rate-limit, replay, races; XSS, инъекции, SSRF, path traversal, unsafe redirects, mass assignment, protobuf/JSON parsing, небезопасную десериализацию, upload/content-type/file-size, WebSocket/realtime subscriptions, multi-user leaks; secrets и environment variables, debug/log leaks, PII, retention, TTL и уничтожение данных.

Проверь dependency vulnerabilities, supply chain, транзитивные зависимости, lockfiles, SBOM, лицензии, GitHub Actions permissions, third-party actions, pinning, untrusted PR execution, secrets in CI, контейнерные образы и инфраструктуру. Если доступно, используй подходящие SAST/SCA/secret scanning/config scanning без публикации секретов. Секреты никогда не вставляй в отчёт и prompt-файлы; описывай безопасными идентификаторами/маскировкой.

Любую критическую уязвимость оформляй как приоритетный пункт с безопасной стратегией устранения и регрессионными тестами. Не проводи эксплуатацию на публичных системах, не эксфильтрируй данные, не раскрывай реальные ключи.
6. BACKEND / DISTRIBUTED SYSTEMS
Для каждого существующего .NET-сервиса и общей библиотеки проверь: границы ответственности, DI lifetimes, singleton/scoped/thread safety, validation, authorization, DTO mapping, nullability, exception handling, cancellation tokens, timeouts, API error contracts, idempotency, retries, circuit breakers, backpressure, graceful shutdown, health/readiness/liveness, structured logging, tracing, metrics, конфигурацию и возможные утечки памяти/ресурсов.

Особое внимание — совместной корректности: HTTP ↔ gateway ↔ gRPC ↔ RabbitMQ ↔ PostgreSQL ↔ Redis ↔ realtime. Проверь доставку и обработку сообщений при at-least-once semantics, deduplication/inbox/outbox (только если оправдано), correlation/causation IDs, ordering, poison messages/DLQ, acknowledgement, повторную обработку, межсервисные транзакции, eventual consistency, cache invalidation/stampede, публикацию события до/после commit, reconnect, WebSocket subscriber authorization и обработку задержек.

Не внедряй Kafka, Kubernetes, event sourcing, CQRS, микросервисы сверх существующих, новую библиотеку или универсальный framework только ради «красивой архитектуры». Каждое предложение сравни с более простым вариантом, оцени стоимость, риски миграции и пользу.
7. DATABASE / PERSISTENCE / DATA INTEGRITY
Исследуй реальные схемы PostgreSQL/EF Core и другие источники состояния: миграции вверх и назад, их порядок, null/default/unique/foreign keys, check constraints, правильность каскадов, индексов, N+1, eager loading, query plans, concurrency tokens, isolation, optimistic locking, pagination, keyset-vs-offset, long-running transactions, connection pools, retry policy и data loss scenarios.

Проверь атомарность пользовательских операций, сохранность данных при сбоях, soft/hard delete, права доступа на уровне каждой выборки/команды, race conditions и кэшированную консистентность. Для изменения схемы в будущих пакетах требуй expand → migrate/backfill → contract, rollback/roll-forward план, проверку на тестовых данных и безостановочную совместимость, если релизный процесс её требует. Не запускай реальные production migrations.
8. FRONTEND / UX БЕЗ РЕДИЗАЙНА
Исследуй фактический стек и все routes/pages/components/hooks/stores/styles, SSR/CSR/hydration, bundle splitting, lazy loading, data fetching, кеш, race conditions, stale state, memory leaks, subscriptions, optimistic updates, retries/cancellations, cleanup, async errors, loading/empty/offline/error states, доступность и keyboard navigation.

Разбери каждый реальный пользовательский маршрут: sign up/in/out, задачи, категории, поиск, публичные/приватные элементы, социальные сценарии, уведомления, настройки, аватар/профиль, realtime-обновления и все обнаруженные функции. Сопоставь UI-инварианты и backend permissions. Устранение визуальных проблем допускается лишь точечно, на основе screenshot/baseline и без изменения общего вида. Проверь responsive, touch/mobile, focus traps, ARIA, контраст, reduced motion, прокрутку, popover/modal positioning, hydration mismatch и визуальную стабильность.

Для каждого будущего изменения должен быть план доказательства visual equivalence: screenshots/snapshots по ключевым состояниям и viewport, явный список разрешённых исключений, Playwright e2e, accessibility assertions. Не переписывай дизайнерские решения ради измеримых метрик, если это ухудшает привычный UX.
9. PERFORMANCE / RELIABILITY / OBSERVABILITY
Сначала базовая линия; потом оптимизация. Определи воспроизводимые измерения cold/warm start, p50/p95/p99 latency, client interactions, DB queries, RPS/throughput, CPU, RAM, network, bundle size, Web Vitals, reconnect/recovery, лишние рендеры и ошибки. Разделяй замеры, гипотезы и догадки. Отдельно оцени web performance, backend, БД, обмен сообщениями и end-to-end UX. Для каждого оптимизационного задания укажи benchmark protocol, ограниченные synthetic datasets, сравнение before/after и порог отсутствия регрессии.

Проверь кэширование, запросы, асинхронность, пул соединений, конкурентность, batching, payload sizes, serialization, очереди, дубль событий, client hydration, UI freezes. Не меняй алгоритмы без проверки семантики. Опиши SLI/SLO, error budget при уместности, безопасные логи без PII, distributed tracing, dashboards, alerts, recovery runbooks и failure injection в изоляции.
10. ТЕСТЫ: ДОКАЗАТЕЛЬСТВО КОРРЕКТНОСТИ, НЕ ПРОЦЕНТ РАДИ ПРОЦЕНТА
Полная инвентаризация текущих unit, integration, contract, component, e2e, security, performance, visual, accessibility и smoke тестов. Для каждого сервиса/функции создай traceability matrix: requirement/invariant → code path → tests → CI job → evidence. Отметь untested critical paths, flaky tests, тесты без важных assertions, ложноположительные тесты, плохие моки и различия локальной/CI-среды.

Спроектируй набор качественных тестов: table-driven/parameterized, property-based, boundary values, null/empty/malformed, permissions matrix (owner/friend/stranger/anonymous), state transitions, time/TTL/time zones, idempotency, retry, concurrency/races, duplicate/out-of-order/lost events, disconnect/reconnect, database transactions, cache invalidation, API contracts, schema migrations, backward compatibility, Unicode, large payloads, browser/mobile matrices и security regression. Для интеграций предложи Testcontainers или аналог только если реально совместим и рационален, с PostgreSQL/Redis/RabbitMQ по нужным сценариям. E2E Playwright — с устойчивыми селекторами и детерминированными ожиданиями.

Укажи желаемые coverage gates по реальному risk profile, branch coverage, mutation testing для критической логики, изменённого кода и доменных инвариантов. Не подменяй тестирование бессмысленными тестами ради формального 100%. Каждый найденный баг должен иметь план regression test: красный до исправления, зелёный после. Тестовые наборы должны быть реалистичными, быстрыми на PR и расширенными по расписанию/перед релизом.
11. CI/CD / GITHUB / REPRODUCIBILITY
Прочитай все реальные .github/workflows/*, reusable workflows, composite actions, build/test scripts, package managers, lockfiles, project configs и deploy instructions. Сопоставь точные локальные команды с CI, среды, SDK versions, переменные, seed data, test filters, build configurations, generated artifacts и триггеры. Нужно добиться воспроизводимости и фактического соответствия проверок: локально и на GitHub проверяется сопоставимый код с эквивалентными условиями.

Оцени: least-privilege permissions, protection от injection через events/PR, зависимостей third-party actions, concurrency cancellation, fail-fast vs coverage, caches, matrices, artifact retention, coverage reporting, formatting/lint/typecheck/security scans/build/test/e2e/dependency updates, required checks, release protection, deployment rollback, status checks и branch protection. 14. ИСПОЛНИТЕЛЬНЫЕ ПАКЕТЫ ДЛЯ МЕНЬШИХ МОДЕЛЕЙ
Это центральный результат. Создай не менее 12 тематических Markdown prompt-файлов, если фактический масштаб проекта это оправдывает; при большом объёме дели области на дополнительные пачки. Пакеты должны быть реально содержательными — не однотипные шаблоны с переименованным заголовком. Они должны снижать необходимость повторного архитектурного обдумывания исполнителем. Важно: если у тебя не хватает фактов, сначала углуби исследование, а не выдумывай точные правки.

Рекомендуемые направления, адаптируй к фактической структуре:
- Foundations / shared contracts / architecture / cross-cutting code;
- Authentication / authorization / privacy and user data;
- Tasks / domain invariants / commands and queries;
- Categories / ownership / access control;
- Messaging / RabbitMQ / event delivery / idempotency;
- Realtime / WebSocket / client synchronization;
- Gateway / gRPC / resilience / API contracts;
- PostgreSQL / EF migrations / integrity / performance;
- Redis / caching / TTL / consistency;
- Frontend core architecture / data fetching / state lifecycle;
- Frontend screens / navigation / search / notifications / accessibility / visual regression;
- Security hardening / supply chain / privacy verification;
- Tests / test infrastructure / coverage and reliability;
- CI/CD / GitHub Actions / environment parity;
- Documentation / developer experience / operational playbooks;
- Cross-system end-to-end verification, performance and final integration.
Если одна область отсутствует, исключи её с обоснованием. Если область слишком велика, раздели на несколько prompt-файлов и оставь работу без пересечений. Межсервисные задачи выделяй отдельно с явно названным ответственным пакетом. Не допускай двух параллельных исполнителей, меняющих одни и те же файлы без координации.
В КАЖДОМ PROMPT_XX_*.md ОБЯЗАТЕЛЬНО:
1. Роль исполнителя и цель: границы пакета, ожидаемый проверяемый результат, приоритеты и критерии принятия решений.
2. Зафиксированный baseline: repository/branch/HEAD SHA на момент планирования и инструкция перепроверки актуального HEAD исполнителем. Не привязывайся к несуществующим файлам.
3. Результаты предварительного исследования: фактическая карта затрагиваемых директорий, файлов, типов, методов, endpoints, tables, events и их назначение. Ссылки на evidence/line numbers, зависимости от других областей.
4. Точный перечень работ с ID, порядком, priority, dependency, scope; для каждого подтверждённого дефекта: как воспроизвести, почему он возникает, какие именно файлы/символы менять, предполагаемое исправление по шагам, границы изменений, security/UX/data implications, какие тесты написать/поправить и точные команды проверки. В сложных случаях — конкретный псевдокод, контракт, алгоритм или схематический diff; не генерируй фиктивные патчи.
5. Точное определение готовности: passing gates, тестовые сценарии, безопасность, отсутствие визуальных и контрактных регрессий, производительность, миграции, качество логов, документация и acceptance criteria.
6. Инструкция исполнителю: вначале проверить реальные пути/символы и сравнить с baseline; при расхождении не слепо исполнять устаревший план, а безопасно переоценить этот пункт. Исполнитель вправе думать и обязан останавливать опасные/неверные инструкции.
7. Локальный runbook: предварительные условия, точные команды (только реально существующие), порядок red → green → refactor → validation, как собирать evidence. Для недоступных команд — условный блок с явной пометкой NOT_VERIFIED.
8. Change boundaries: что можно менять, что запрещено, какие общие файлы находятся под отдельным ownership, какие API/UX инварианты соблюдать.
9. Risk / rollback / deployment note: регрессии, миграции, обратная совместимость, пути отката, план смягчения.
10. Формат отчёта исполнителя: перечень изменённых файлов, commands/results, tests, coverage evidence, measured before/after, unresolved items, commits/PR links (если разрешены), artifacts.
11. Чеклист завершения с однозначными pass/fail критериями и запретом объявлять успех без выполнения проверок.
12. Оценка трудоёмкости и размера контекста, возможность разделить на независимые подзадачи без нарушения зависимостей.
Промпты должны быть самодостаточными для другой модели, но не дублировать гигантские общие правила дословно: создай единый EXECUTOR_CONTRACT.md, а в пакетах давай краткую обязательную ссылку/указание прочесть его целиком. Если исполнитель может получить только один файл, предусмотрительно добавь в него минимальный автономный контракт. Не делай пакеты искусственно длинными — высокая детализация должна приходиться на факты, решения и исполняемые шаги, а не на повторение пафоса.
15. РАСПИСАНИЕ, ЗАВИСИМОСТИ И СТАНДАРТ ПРИЁМКИ
Построй DAG задач, выдели стадии: baseline & diagnostics → security blockers → contracts/data integrity → isolated service fixes → frontend fixes without redesign → test expansion → CI parity → documentation → E2E/performance/regression hardening → integration review. Если реальная зависимость требует другой очередности, исправь граф и объясни. Отдели параллелизуемые пакеты от строго последовательных. Составь критический путь, risk-based приоритет (P0/P1/P2/P3), stop-the-line события и checkpoint после каждой фазы.

Опиши две модели исполнения: (A) последовательная, наиболее безопасная; (B) ограниченно параллельная с выделением ownership по файлам/контрактам и обязательной интеграционной проверкой. Не требуй переезда на новую веточную стратегию без запроса владельца. Опиши работу через изолированные рабочие ветки/PR, но финальные merge/branch cleanup — только с разрешения и после всех обязательных checks.

Каждый пакет должен иметь preconditions, inputs, outputs, blocked_by, acceptance, rollback, estimated_size, risk, owner_scope. Для каждого этапа — точный артефакт, который следующая модель должна прочитать перед началом.
