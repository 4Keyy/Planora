## DIST-008

`CacheService.RemoveAsync` удаляет запись из L1 текущего экземпляра в `finally`.
Ошибка L2 логируется. `OperationCanceledException` доходит до вызывающего кода.
Get и Set также сохраняют отмену. Вызов удаления по шаблону проверяет отмену
до ранних выходов. `CacheInvalidator` сообщает о попытке, поскольку API удаления
сохраняет контракт best effort. Если L2 сохранил значение, следующий запрос может
снова загрузить его. При независимом L1 во втором процессе его запись остаётся
до собственной инвалидации или TTL.

Поиск `ICacheService` и `ICacheInvalidator` по tracked C# и текущим исходникам
нашёл регистрацию DI, реализации, вызов CacheService из CacheInvalidator и тесты.
В прикладных путях вызовов нет. P3 сохраняется. UI, публичный API, DI-сигнатуры и
контракты безопасности вне изменения. Screenshot matrix N/A.

## OPS-013. Хранилище Data Protection

В Compose Auth получает `ConnectionStrings__Redis` от общей инстанции.
`AddDatabase` создаёт отдельное подключение к тому же endpoint для
`Planora:Auth:DataProtection-Keys`. `AuthDbContext` использует этот provider
для шифрования TOTP secrets. При утрате нужного ключа
`UnprotectSafe` возвращает null. Security stamps имеют отдельные ключи с TTL
120 минут, blacklist использует IDistributedCache с TTL токена. При включённом
Redis backend rate limiter использует raw multiplexer. Ни один из этих путей
не проходит через CacheService.

На двух изолированных Redis 7.4.8 с AOF и лимитом 4 MiB выполнили по 48 записей
объёмом 128 KiB. При `allkeys-lru` Redis принял все записи и вытеснил 32 ключа,
включая контрольный список без TTL. При `noeviction` список сохранился, 31 запись
получила OOM. Контейнеры были без сети и host mounts, после прогона удалены.
Это проверка политики под управляемой нагрузкой. Ёмкость рабочих инстансов,
данные TOTP и фактическая production-конфигурация остаются непроверенными.

Для T02/T14 подготовить отдельное долговечное хранилище key ring с контролем
ёмкости и запретом вытеснения ключей. До переключения проверить резервную копию,
перенос существующих ключей и расшифровку заранее созданного синтетического TOTP
после рестарта и восстановления. Сохранить application name и purpose, задать
защиту ключей в хранилище. Согласовать совместимость реплик при смене provider.
Для stamp/blacklist и rate limit отдельно определить обработку OOM, недоступности
и потери состояния. Переключение общего Redis требует своих capacity и failure
проверок. Runtime и настройки рабочего Compose не менялись.

T15 получает failure contract L1/L2, границу независимых экземпляров и handoff
по Redis. Откат cache change возможен по собственному коммиту. Перенос key ring
требует сохранения обоих наборов ключей для расшифровки существующих данных.
