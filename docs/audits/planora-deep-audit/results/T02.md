# T02. Auth session lifecycle и проверка хешей

## Дополнение 2026-11-06: gate облачного запуска

Проверка access-token stamp теперь отклоняет запрос при недоступном Redis,
ошибке lookup, повреждённом непустом значении или некорректном principal.
Успешный lookup без ключа остаётся допустимым: штамп хранится только после
security event и имеет TTL. Regression: RED 15/28 → GREEN 33/33, включая
настоящие JWT с обоими режимами claim mapping.

Reset/change password, revoke-all и refresh replay передают stamp callback в
существующую транзакцию. Он выполняется после revalidation и SQL mutation,
под пользовательским advisory lock, до commit. Ошибка/отмена stamp откатывает
SQL. Если stamp записан, а commit завершился ошибкой, допускается консервативная
инвалидация access tokens без сохранения изменения в БД. Старые overloads
сохраняют поведение для остальных callers.

Provider RED: 4/4 новых сценария подтвердили старый post-commit gap. GREEN:
66 transaction/handler проверок; расширенный Auth scope — 483 passed,
0 failed/skipped на отдельном PostgreSQL fixture. Проверены lock, отсутствие
внешней видимости SQL до callback, rollback при stamp error/cancellation и
ошибке commit. Это не доказывает атомарность Redis и PostgreSQL при потере
состояния самим Redis.

ChangeEmail, Disable2FA и DeleteUser переведены на тот же helper с revalidation
под lock, stamp перед commit и проверкой результата при неоднозначном commit.
RED трёх оставшихся путей: 3 failed; итоговый Auth scope: 494 passed,
0 failed/skipped. Проверены success/stale password для каждого пути, rollback
пользователя и outbox, сохранение avatar при stamp failure и bounded cleanup
после успешного commit, независимо от отмены исходного HTTP-запроса.
Outbox pulse может предшествовать outer commit; штатный polling подбирает запись.

## BE-003. Ротация refresh token и replay

Два независимых Npgsql-контекста прочитали одну активную запись до начала записи.
Без fingerprint оба запроса вернули успех. С fingerprint проигравший получил
`REFRESH_ERROR`. Тест replay на промежуточной реализации показал отдельную гонку.
Между чтением replay-запроса и отзывом цепочки следующий токен успевал
ротироваться. Новый потомок оставался активен, а причина отзыва его родителя
перезаписывалась.

Репозиторий условно отзывает запись по ID, хешу и состоянию до вставки замены.
Обе операции проходят в одной транзакции с retrying execution strategy.
При потере подтверждения коммита проверяется ID и хеш ожидаемого потомка.
Проигравший читает актуальную строку. Если хеш принадлежит ранее
ротированной записи, применяет существующую политику replay. Отзыв живых
токенов и ротация берут один транзакционный PostgreSQL advisory lock на
пользователя. Redis stamp обновляется после сохранения отзыва. Кандидат
access token вычисляется до коммита, чтобы штамп от конкурирующего replay
мог его инвалидировать. Ответ с токенами формируется после успешной записи.

Сценарии с fingerprint и без него дают ровно один успех. Отдельные тесты
воспроизводят rollback после условного отзыва при ошибке и отмене вставки.
Проверка через `pg_locks` наблюдает ожидание replay до завершения ротации.
Последующий отзыв охватывает нового потомка и сохраняет причину отзыва
предыдущего поколения. Политика выдачи при недоступности Redis и остальные
писатели сессий требуют отдельных проверок. Stamp и выдача токенов в provider
сценариях используют тестовые сервисы.

## BE-004. Вход с того же устройства

Истёкшая nonrevoked запись блокировала INSERT с `23505` на
`ix_refresh_tokens_user_device_active`. При выдаче новой записи транзакция
сначала отзывает истёкшую запись того же пользователя и устройства.
При обычном повторном входе транзакция удерживает строку и проверяет
предыдущий хеш перед обновлением. В обоих случаях существующие обновления
пользователя сохраняются в той же транзакции. Нуждающийся в rehash пароль
обновляется только с успешным входом.

При двух одновременных запросах, которые прочитали одно состояние устройства,
проигравший получает `LOGIN_SESSION_CHANGED` через существующую 401-ветку
контроллера. В тестах активная сессия переиспользует ID, истёкшая получает
маркер отзыва, прежняя отозванная строка и другое устройство сохраняются.
RememberMe и параметры cookie сохранены. Отдельно проверен один успешный
аудит входа в каждом конкурентном сценарии. Проверка логина через браузер
не выполнялась. Визуальных изменений нет.

## BE-013. Повреждённая запись PBKDF2

Тесты также воспроизвели принятие неподдерживаемой версии и маркеров при

в рабочий User и удалённый ввод хеша не установлены.

## Одноразовые recovery и reset tokens

В PostgreSQL две попытки с одним recovery code и две попытки с одним reset token
возвращали по два успеха. Две дополнительные гонки reset затрагивали новый токен,
выпущенный после чтения прежнего. Контроль неправильного владельца, неправильного
и использованного кода и отмены прошёл. Исходный прогон дал 4 failed и 1 passed.

Recovery code теперь потребляется условным UPDATE по владельцу, ID, хешу и
состоянию. Аудит `UsedAt`, `UpdatedAt` и `UpdatedBy` сохраняется. Reset проверяет
текущий хеш и срок действия под блокировкой, перечитывает связанные сессии и
применяет доменную смену пароля и отзыв сессий в одной транзакции. Доменное
событие, stamp и письмо следуют за коммитом. Запоздалая очистка истёкшего токена
применима только к прежнему хешу. Выпуск нового reset token записывает только
изменившиеся поля и сохраняет пароль, который уже сменил другой запрос.

## BE-014. Активная связь для пары пользователей

Пять исходных сценариев PostgreSQL упали. Два параллельных запроса
создавали по две заявки в одном направлении и во встречных направлениях.
При наличии исторической Rejected-записи поиск пропускал Pending или Accepted.
Оба способа отправки теперь используют один транзакционный advisory lock для
упорядоченной пары GUID. Запрос статуса после блокировки выполняется отдельной
командой в Read Committed. Вставка и проверка существующей связи входят в эту
транзакцию. При неопределённом результате коммита стратегия проверяет ID
кандидата. Поиск для удаления связи предпочитает Accepted, затем Pending.

GUID-ветка сохраняет `PENDING_REQUEST` и `ALREADY_FRIENDS`. Email-ветка
возвращает тот же общий результат для отсутствующего адресата и повтора.
При конкуренции событие об отправке записывает только победитель.
Тест отмены перед INSERT проверяет пустое состояние, отсутствие события и
успешный повтор в том же контексте. Всего 68 адресных и 1459 расширенных тестов
прошли без пропусков. Первый запуск остановился на копировании DLL, которые
удерживали работающие сервисы. Повтор использовал отдельный `OutDir`.
[RED, GREEN и результаты ревью](evidence/t02-friendship-verification.json)

Схема и существующие данные сохранены. Блокировка координирует два
обновлённых пути приложения. Старые бинарники и прямой SQL её обходят.
Фактическую потерю подтверждения коммита отдельно не инъецировали.
Список исходящих заявок остаётся отдельной границей приватности. По наличию
заявки и её DTO верифицированный отправитель может установить, найден ли
адресат. Наблюдение подтверждено трассировкой источников.

## BE-020. Вход после смены проверенного пароля

В двух исходных тестах PostgreSQL login проверял прежний пароль, ждал на
этапе 2FA, а затем продолжался после успешного reset и вызова stamp. Обе
попытки создавали новую активную сессию на другом устройстве. В варианте с
rehash запись также восстанавливала прежний пароль.

В транзакцию входа передаётся хеш, фактически проверенный до rehash. Login
берёт тот же advisory lock пользователя, что reset и refresh, затем
блокирует активную строку пользователя с этим хешем. Только после этого
проверяет поколение сессии и сохраняет изменения. Оба теста теперь получают
`LOGIN_SESSION_CHANGED`, оставляют новый пароль и одну отозванную сессию,
без записи об успешном входе. Одновременный rehash в другом запросе также
может потребовать повторить вход через существующий 401-контракт.

Auth 465/465, расширенный UnitTests 1461/1461, ErrorHandlingTests 94/94.
Пропусков в этих выборках нет. Широкая выборка исключает отдельный RED
аватара и два оркестрируемых теста рестарта из T05. Независимый обзор
проверил порядок блокировок и результат обеих гонок. Stamp в сценарии
заменён тестовым сервисом. [Команды и TRX](evidence/t02-login-reset-verification.json)

## BE-016. Публикация и очистка аватара

Исходный тест с ошибкой сохранения профиля оставлял в записи старый URL
после удаления файла. Теперь варианты публикуются через временные файлы
в том же каталоге. Загрузка удерживает файловую блокировку от чтения
профиля до сохранения URL и последующей очистки. Сохраняются только
изменившиеся поля отслеживаемой записи. Отдельный экземпляр хранилища
ждёт ту же блокировку при удалении и поддерживает отмену ожидания.

Удаление аккаунта сохраняет состояние и staged outbox одной операцией.
При ошибке сохранения очистка пропускается. После коммита отмена запроса
на этапе stamp не отменяет очистку. Очистка имеет собственный таймаут 10 с,
а ошибки по-прежнему передаются на повтор в retention.

Адресные проверки 55/55, расширенные 1464/1464. Пропусков в этих выборках
нет. Первый адресный прогон без PostgreSQL пропустил четыре проверки
retention. В промежуточных прогонах проверка обнаружила раннюю очистку
и устаревший mock-контракт outbox. Они исправлены до повторного прогона.
Расширенная выборка исключала отдельные RED проверки смены пароля и
отзыва сессий, а также два оркестрируемых сценария рестарта из T05.
[Команды, TRX и ревью](evidence/t02-avatar-verification.json)

Проверка файлов выполнена в Windows и временном каталоге. Координация
требует общего тома, поддержки файловой блокировки и обновлённых писателей.
Межпроцессный запуск на Linux, раздельные тома и сбой питания не проверены.
При неопределённом исходе сохранения новая ревизия может остаться до
следующей успешной замены или удаления аккаунта.

## BE-026. Смена пароля и отзыв всех сессий

Два PostgreSQL-сценария подтвердили, что после успешных операций записи
активных refresh tokens сохранялись. Обработчики загружали пользователя
без сессий, а доменный отзыв проходил по загруженной коллекции.

Смена пароля, reset и отзыв всех сессий теперь используют одну границу
сохранения. Внутри транзакции берётся блокировка пользователя, проверяется
текущий хеш или reset token и загружаются активные сессии. Смена пароля
сохраняет пароль, отзыв и последние пять записей истории одним коммитом.
Доменное событие и stamp следуют за коммитом. Провайдерные тесты
проверяют обе сессии владельца, сохранность истории и чужой записи.
Отдельный сценарий подтвердил, что запоздалая смена пароля сохраняет
результат конкурентного reset.

Адресный Auth 471/471 и широкий UnitTests 1467/1467 без пропусков.
Два промежуточных прогона нашли устаревшие настройки mock-фикстур,
их привели к новой транзакционной границе. Широкий прогон исключал
два оркестрируемых сценария рестарта, проверенные в T05.
[RED, GREEN и ревью](evidence/t02-revocation-verification.json)

## BE-027. Отзыв одного поколения сессии

В PostgreSQL logout прочитал прежний токен, после чего повторный login
на том же устройстве успешно сохранил новое поколение. Запоздалый logout
перезаписал новую строку прежним снимком и отозвал её. Контроль чужого
владельца прошёл на исходном коде.

Logout и отзыв одной сессии теперь выполняют условный UPDATE по ID,
владельцу, прочитанному хешу и активному состоянию. Обновляются только
поля отзыва. При сменившемся поколении logout сохраняет идемпотентный
успех, а отзыв по ID возвращает существующий `SESSION_INACTIVE`.
Текущий контроллер переводит такую failure в HTTP 400.

Четыре provider-проверки подтверждают оба запоздалых пути, сохранность
чужих записей, отмену и повтор. Auth 475/475 и широкий UnitTests 1471/1471
прошли без пропусков. Два сценария рестарта брокера проверены отдельно
в T05. Независимое ревью не обнаружило блокирующих замечаний.
Потеря подтверждения UPDATE отдельно не инъецировалась. При ней повтор
может вернуть `SESSION_INACTIVE` после фактически успешного отзыва.
