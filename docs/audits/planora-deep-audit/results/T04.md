# T04 - Category deletion and its outbox message

## 2026-11-20

BE-001 covers the normal owner deletion path. It used to commit the category
and dispatch the domain event afterward. The dispatcher opened another
scope and the handler saved its outbox row there. A failure between those
saves could strand Todo category references.

Commit [70f44cd9](https://github.com/4Keyy/Planora/commit/70f44cd9a7423afabf15023578b004dac97bbb28) stages
the deletion message in the Category context that saves the soft deletion.
The context keeps the domain event available after a failed save and detaches
the staged message so a retry can write one row. The message type and ID
fields remain compatible with the Todo consumer. Owner checks still run
before the category is marked as deleted. The account-erasure path uses
its existing user-deletion event.

| Verification | Result |
| --- | --- |
| EF InMemory failure injection | The regression failed on the original source because there were zero outbox rows staged at the owner save. The corrected code staged one row before the synthetic failure, retained the previous persisted state and committed one deletion and one message on retry. |
| Release build | Passed with six existing deprecation warnings and zero errors. |
| Targeted tests | 109 Category, application, logging and retention cases and 59 Collaboration cases passed in the local in-process harness. VSTest's local test-host connection is restricted in this session. |
| PostgreSQL rollback | Added a provider regression that rejects the outbox insert in a temporary database, checks rollback from another context and verifies the retry. The scenario still needs a database-enabled run. |

The EF model is unchanged. T04 remains open for the PostgreSQL rollback
regression and the other checks in the [package plan](../PROMPT_04_CATEGORIES.md).
