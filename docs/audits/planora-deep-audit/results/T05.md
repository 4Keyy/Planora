## Findings, implementation and boundaries

**DIST-001:** `SubscribeAsync` and `UnsubscribeAsync` now require a stable logical
`subscriptionId`. All 13 startup subscriptions and the test bus implementation were
updated. Independent services have distinct IDs; replicas share an ID and queue
`planora.<id>.v1`. Queue identity no longer depends on a handler class name.
Normal event routing keys and payloads are unchanged.

Each callback captures exactly its typed handler. The former event-wide handler list
caused every queue for an event to invoke all its local handlers. The new registration
also rejects ID/type reuse, serializes concurrent setup, permits retry after failed or
canceled setup, disposes failed channels and targets exact unsubscribe operations.
Missing handlers and null JSON can no longer be acknowledged as successful handling.

**DIST-002:** every subscription creates a durable quorum DLQ and explicit DLX binding
before consuming. The durable quorum source declares its DLX, a subscription-specific
dead-letter routing key, `x-dead-letter-strategy=at-least-once` and
`x-overflow=reject-publish`. Poison JSON is quarantined immediately; transient failure
requeues once, then quarantines. Persistent publication retains mandatory routing and
tracked publisher confirms. A returned publication still throws and does not mark a
persisted outbox row Processed.

The narrow shared-interface handoff covers `Application/Messaging/IEventBus.cs`,
`Infrastructure/Messaging/RabbitMqEventBus.cs`, Todo/Category/Collaboration/Realtime
`Program.cs` subscription calls and `TodoApiTestFactory.MockEventBus`. Test additions
are `RabbitMqSubscriptionTests.cs`, `RabbitMqLiveTests.cs` and
`UserDeletionRabbitPostgresTests.cs`. No working queues were modified or deleted.

Historical inbox keys remain based on event ID and handler type for compatibility.
The optional inbox still records best effort; handler renaming, atomic domain/inbox
transactions and parallel duplicate effects require separate contracts and checks.
This change does not establish exactly-once delivery or processing.

## Transition, risks, documentation and rollback

[Prepared topology transition](evidence/t05-topology-transition.md) maps all 13 new
subscriptions to 11 legacy queue names. It requires observed inventory, compatible
declarations, approved producer/consumer pauses, preserved legacy backlog, bounded
copy replay with original IDs and per-domain effect acknowledgements. It supplies no
automatic working replay utility and performs no migration. The original collided
queue cannot identify which domain processed a previously acknowledged event.

Operational acceptance remains **BLOCKED pending T14 and owner approval**. Complete
historical payload provenance and all domain effects must be reconciled before closing
the historical finding; zero queue depth and publisher confirms are insufficient.
Cluster availability, capacity behavior during prolonged DLQ outage, process kill
between domain commit and ACK, and production recovery were not exercised here.

Quorum support, `stream_queue`, durable storage, resource headroom and effective queue
policies are deployment prerequisites. An incompatible existing queue blocks startup
declaration; do not resolve it by deletion or by downgrading delivery guarantees.

bounded retry and remaining optional-inbox semantics in architecture and operations docs.
T14 delta: final-SHA topology preflight, capacity/alerts, compatible rollout, preserved
backlog and approved historical replay. Rollback must preserve both old/new queues and
their data; reverting to the old collided consumer naming is unsafe. Prefer reviewed
roll-forward on the new topology.
