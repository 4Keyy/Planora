| Тесты | Vitest: мок двух страниц (100 + 50, `totalCount = 150`) → 150 задач в состоянии. E2E API: создать 101 задачу и сверить число карточек |

### FE-12. Параллельный refresh в нескольких вкладках может отозвать все сессии пользователя

| | |
|---|---|
| Категория · критичность · приоритет · сложность | Потенциальный риск · **Высокий** · P1 · M |
| Где | `frontend/src/lib/auth-public.ts:18`, `:107–113` (single-flight только внутри вкладки); `frontend/src/store/auth.ts:283–299` (`restoreSession`), `:309–337` (плановый refresh); `frontend/src/lib/api.ts:276–279`; `Services/AuthApi/Planora.Auth.Application/Features/Authentication/Handlers/RefreshToken/RefreshTokenCommandHandler.cs:65–88` |
| Как сейчас | Каждая вкладка обновляет токен независимо, общая cookie у всех вкладок одна. Бэкенд при предъявлении уже ротированного refresh-токена считает это кражей: отзывает все активные refresh-токены пользователя и меняет security stamp, без окна снисхождения |
| Почему проблема, последствия | Если два запроса `/auth/refresh` уходят почти одновременно с одной cookie, второй выглядит как повторное использование. Это возможно, когда браузер восстанавливает несколько вкладок после перезапуска, когда плановые таймеры вкладок совпали или когда две вкладки одновременно получили 401. Итог — выход на всех устройствах без причины со стороны пользователя |
| Воспроизведение, доказательство | Механизм подтверждён кодом обеих сторон; последствие — потенциально, зависит от того, как упорядочатся коммиты в БД. Проверка на уровне API: два параллельных `POST /auth/refresh` с одной cookie → второй 401, все токены отозваны. В браузере: две вкладки, перезапуск браузера с восстановлением сессии |
| Решение, преимущества | Координация между вкладками через Web Locks API: `navigator.locks.request("planora:auth-refresh", ...)` вокруг `requestAccessTokenRefresh`. Внутри блокировки повторно проверить, не обновила ли токен другая вкладка, и разослать новый access-токен через `BroadcastChannel` (тот же origin, только память). Защита в глубину на бэкенде: короткое окно (10–30 с), в которое предъявление только что ротированного токена с того же устройства не отзывает цепочку |
| Риски, влияние | Web Locks поддерживается всеми актуальными браузерами; нужен фолбэк без блокировки (текущее поведение) |
| Бэкенд | Желательно (окно снисхождения) |
| Тесты | Vitest с моком `navigator.locks`: две «вкладки» → один запрос refresh. Playwright: два `page` в одном контексте одновременно получают 401 → оба продолжают работу. xUnit на окно снисхождения |
| Видимость | Исправление дефекта (исчезают неожиданные выходы) |
